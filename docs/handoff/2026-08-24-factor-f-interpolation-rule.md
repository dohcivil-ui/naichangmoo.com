# Handoff — `v0.24.0: A Factor Between Two Steps Is Now a Rule, Not a Habit`

## Description

ตาราง Factor F พิมพ์ค่างานไว้เป็นขั้น (0.5, 1, 2, 5, 10 … ล้านบาท) แต่ค่างานจริงแทบไม่เคยตรงขั้น
คำถามว่าจะใช้ค่าไหนจึงเกิดกับเกือบทุกโครงการ และหลักฐานสองอย่างขัดกัน: หมายเหตุข้อ 1 ใต้ทุกตารางสั่งให้
เทียบอัตราส่วน ส่วน ปร.4 ของโครงการจริงที่ผ่านการตรวจใช้ค่าของขั้นที่ต่ำกว่า

เจ้าของงานตัดสินว่า **ยึด ว481** คือทำตามหมายเหตุ คำตัดสินนี้ถูกบันทึกเป็นกฎคู่กับกฎเรื่องหนังสือเวียนฉบับล่าสุด
พร้อมข้อกำหนดที่ตามมาจากมันโดยตรง

## ผลที่ต้องเตรียมคำอธิบายไว้

**ระบบจะให้ตัวเลขไม่ตรงกับ ปร.4 ที่ทำด้วยมือและผ่านการตรวจมาแล้ว**

| | Factor F | ค่าก่อสร้าง | ยอดสุทธิ |
|---|---|---|---|
| ปร.4 ของอาคารฟอกไต ปุญโญภาส | 1.3034 (ค่าของขั้น 2 ล้าน) | 3,296,598.64 | 3,296,500 |
| ระบบตามกฎนี้ | 1.3028 (เทียบอัตราส่วน) | 3,295,081.10 | **3,295,000** |

ต่างกัน **1,500 บาท** และระบบให้ตัวเลขที่**ต่ำกว่า** เพราะการหยิบค่าของขั้นที่ต่ำกว่ามาใช้ทำให้ตัวคูณสูงเกิน
ที่หลักเกณฑ์กำหนด คำอธิบายที่ยืนได้คือระบบทำตามหมายเหตุที่พิมพ์อยู่ในหนังสือเวียนฉบับที่ใช้บังคับ

**ตัวเลข 1,500 นี้ต่างจาก 1,400 ที่บันทึกไว้ใน handoff ของ v0.22.0** เพราะตอนนั้นคำนวณด้วยค่า 1.302835
แบบไม่ปัด ส่วนกฎที่ตัดสินแล้วให้ปัดเป็นสี่ตำแหน่ง (1.3028) ก่อนคูณ ตัวเลขที่ถูกต้องคือ 1,500

## ข้อกำหนดที่ตามมาจากคำตัดสิน และเหตุผลของแต่ละข้อ

1. **ปัดเป็นทศนิยมสี่ตำแหน่งก่อนคูณ** — ปร.5 พิมพ์ Factor F ไว้สี่ตำแหน่งแล้วคูณด้วยเลขที่พิมพ์
   ถ้าระบบเก็บทศนิยมมากกว่าที่แผ่นแสดง แผ่นจะตรวจเลขของตัวเองไม่ผ่าน
2. **หนึ่ง Factor F ต่อหนึ่งหมวดงาน เลือกจากค่างานรวมของหมวด** ไม่ใช่เลือกรายบรรทัด
   การเลือกรายบรรทัดจะได้ยอดรวมที่ยังดูสมเหตุสมผลแต่ผิด
3. **ผลลัพธ์ต้องบอกได้ว่าตัวคูณมาจากขั้นที่พิมพ์หรือจากการเทียบอัตราส่วน พร้อมสองขั้นที่คร่อมอยู่** →
   ยกเป็น **IP-073** เพราะวันที่ถูกซัก ผู้ใช้ต้องชี้ที่มาได้ทันที ไม่ใช่เห็นแค่ 1.3028 ลอย ๆ
   โครงสร้างที่ `resolveFactorF` คืนออกมารองรับอยู่แล้ว (`basis`, `row`, `nextRow`) เหลือแต่การแสดงผล
