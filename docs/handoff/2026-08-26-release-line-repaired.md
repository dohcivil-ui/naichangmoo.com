## เรื่องย่อ

เจ้าของงานเปิดหน้า repo แล้วถามว่าทำไม release ล่าสุดยังเป็นของเก่า ตรวจแล้วพบว่า
**บันไดของเลขรุ่นห้าขั้นหลุดกันคนละจุด** และไม่มีใครรู้มาสองวัน

| บันได | หยุดอยู่ที่ | ตามหลัง |
|---|---|---|
| GitHub Releases | v0.20.0 | **25 รุ่น** |
| git tag | v0.34.0 | 11 รุ่น |
| CHANGELOG.md | v0.33.0 | 12 รุ่น |
| package.json | 0.33.0 | 12 รุ่น |
| roadmap.json | v0.45.0 | เป็นตัวตั้ง |

เรื่องนี้สำคัญเพราะ **วิธีย้อนกลับของโปรเจกต์นี้คือ `git checkout` ไปที่ธงที่ระบุไว้ใน handoff**
รุ่นที่ไม่มีธงจึงไม่มีทางกลับ และหน้าที่คนเปิด repo เห็นเป็นอย่างแรกคือ GitHub Release
ซึ่งเป็นบันไดที่ล้าหลังที่สุด

**สาเหตุที่พังเงียบ:** `scripts/check-roadmap.mjs` ตรวจแค่ว่าแผนตรงกับสำเนาของแผน
ไม่มีอะไรตรวจว่า **สิ่งที่ประกาศออกไปข้างนอกตรงกับแผน** ทั้งสามอย่างจึงเลื่อนหลุดได้ทีละรุ่น

## อะไรถูกแก้

**หนึ่ง — คืนกฎที่ถูกละเมิด**
commit `28265d1` ของเซสชันก่อนแก้ `roadmap.v0.45.0.json` ซึ่ง `docs/roadmap/README.md`
ห้ามไว้ว่า "ห้ามแก้ไฟล์รุ่นที่ commit แล้ว ให้สร้างรุ่นใหม่แทน" ไฟล์ถูกคืนสภาพเท่ากับที่ `33ce5ad`
และการเปลี่ยนแปลงย้ายไปอยู่ที่ v0.46.0 ตามที่ควรเป็นตั้งแต่แรก

**สอง — ตัวตรวจที่กันไม่ให้พังซ้ำ**
`scripts/check-release.mjs` ต่อเข้า `hooks/pre-commit` แล้ว ตรวจสามข้อ:
เลขใน package.json ต้องเท่า roadmap · CHANGELOG ต้องมีบรรทัดของรุ่นปัจจุบัน ·
ธงที่ยังไม่มีเป็นคำเตือนไม่ใช่ข้อผิดพลาด (เพราะธงปักหลัง commit เสมอ ถ้าทำให้ล้มจะ commit ไม่ได้เลย)

**สาม — คำสั่งปิดรุ่นคำสั่งเดียว**
`pnpm release` ตรวจให้ครบก่อนแตะอะไร (อยู่บนสายหลัก · working tree สะอาด · ธงยังว่าง ·
สายหลักไม่ตามหลัง origin) แล้วปักธง push และ **สร้าง GitHub Release** ในคราวเดียว
ขั้นสุดท้ายนี้คือขั้นที่หายบ่อยที่สุด เพราะ GitHub Release ไม่ใช่สิ่งเดียวกับ git tag

**สี่ — เติมของที่ขาดย้อนหลัง**
- ปักธง 7 อันให้รุ่นที่มีจุดย้อนกลับจริง: v0.35.0 · v0.37.0 · v0.38.0 · v0.39.0 · v0.40.0 · v0.44.0 · v0.45.0
- สร้าง GitHub Release **23 รุ่น** ที่ขาด ตอนนี้ทุกธงมี Release ครบ
- เติม CHANGELOG 12 รุ่น (v0.34.0–v0.46.0) พร้อมกำกับว่าเติมย้อนหลัง
- ปรับ package.json จาก 0.33.0 เป็น 0.46.0

**ห้า — เอกสารกฎตรงกับการปฏิบัติ**
`docs/rules/engineering.md` · `AGENTS.md` · `PROJECT.md` เคยสั่งว่า "ต้องแตกสาขาก่อนทุกงาน"
ซึ่งเป็นเหตุที่มีสาขาค้าง 13 อัน แก้เป็นสายเดียวปิดจบทุกครั้งตามมติเจ้าของงาน

**หก — เก็บสาขาที่ค้าง**
ลบ 14 สาขาที่ merge เข้าสายหลักแล้ว ทั้งในเครื่องและบน origin
