## สิ่งที่วัดได้จากการลงมือ และเป็นหลักฐานว่าเรานำเขาได้

### หนึ่ง — ตัวสร้างแผนอัตโนมัติของเขา ให้แผนที่ยอดไม่ตรงกับงบที่ผู้ใช้กรอก

**ทำ:** กด `สร้างอัตโนมัติ` เลือกแม่แบบบ้านพักอาศัย 2 ชั้น กรอกงบ **2,500,000** พื้นที่ 160 ตร.ม. เริ่ม 25 ส.ค. 69

**ได้:**

| รายการ | ค่าที่ระบบสร้าง |
|---|---|
| งบประมาณโครงการที่หัวหน้าจอ | **฿2,530,000** |
| หมวดงาน 5 หมวด | 420,000 + 910,000 + 680,000 + 380,000 + 140,000 = **2,530,000** |
| งวดเงิน 5 งวด (อ่านจากรายงาน LINE) | 375,000 + 375,000 + 625,000 + 625,000 + 500,000 = **2,500,000** |
| กิจกรรม | 21 รายการ · 19 จาก 21 มี Total Float 0 วัน |

**ผลคือตัวเลขสามชุดไม่ตรงกันตั้งแต่วินาทีที่สร้างโครงการ** ก่อนผู้ใช้แตะอะไรเลย:
ผู้ใช้กรอก 2.50 ล้าน · เนื้องานรวม 2.53 ล้าน (เกิน 30,000 หรือ +1.2%) · งวดเงินรวม 2.50 ล้าน
แปลว่าเขาแจกค่างานจากตัวเลขกลมตามแม่แบบ แล้วไม่เคยกระทบยอดกลับไปหางบที่ผู้ใช้พิมพ์

> **เทียบกับของเรา:** `activityWeights` แจกน้ำหนักด้วย largest remainder ให้รวมได้ 1,000,000 ppm พอดี
> และ `buildMilestoneSchedule` คิดจากยอดสะสมลบงวดก่อน ทำให้ `totalWorkSatang` เท่ากับ `contractSatang` เป๊ะเสมอ
> มี test ยืนยันอยู่แล้ว ข้อนี้จึงไม่ใช่คำอวด แต่เป็นข้อที่วัดเทียบกันได้ตรง ๆ

**และสองหน้าจอของเขาก็ไม่ตรงกันเองด้วย:** แถวของโครงการเดียวกันในหน้ารายการโครงการแสดงงบ
**฿2,500,000** ขณะที่หัวหน้าจอแผนงานของโครงการนั้นแสดง **฿2,530,000**
แปลว่าเรกคอร์ดโครงการเก็บยอดที่ผู้ใช้กรอก ส่วนหน้าแผนงานบวกจากรายการงานจริง แล้วไม่มีใครกระทบยอดสองอันนี้เข้าหากัน

อีกจุด: กิจกรรม 19 จาก 21 มี Total Float เป็นศูนย์ แปลว่าแผนที่สร้างให้เป็นโซ่เส้นเดียวเกือบทั้งเส้น
งานเกือบทุกงานกลายเป็นงานวิกฤต ซึ่งไม่ใช่รูปร่างของแผนก่อสร้างจริง

### สอง — บั๊กหน่วยเงินล้านเท่า ยังอยู่ และยังอยู่ที่เดิม

การ์ดงวดที่ 1 แสดงสามบรรทัด (ยอดขอเบิก / ยอดรับรอง / เงินเข้าจริง) เป็น **฿305,000,000,000**
ขณะที่ฟอร์มแก้ไขงวดเดียวกันเก็บค่าจริงไว้ `305000` และตาราง S-Curve แสดง `฿305,000` ถูกต้อง
ยืนยันอีกครั้งว่าเป็นบั๊กที่ชั้นแสดงผลของการ์ด ไม่ใช่ที่ข้อมูล

### สาม — บั๊กที่เพิ่งเจอรอบนี้

| # | อาการ | ที่ไหน |
|---|---|---|
| 1 | คอลัมน์ `RATE (฿/H)` แสดงคำว่า **undefined** ทุกแถวทั้ง 29 ทรัพยากร | กำลังคน แท็บ ทีม/ทรัพยากร |
| 2 | ช่อง VAT ในกล่องตั้งค่างวดงาน **ว่างเปล่า** ทั้งที่การ์ดงวดคิด VAT 7% อยู่จริง (ยืนยันซ้ำจากรอบก่อน) | ตั้งค่างวดงาน |
| 3 | หน้าภาพรวมแสดง `การใช้กำลังคน 0%` ขณะที่หน้ากำลังคนบอก `โหลดหนักสุด 280%` | ภาพรวม เทียบกับ กำลังคน |

คำนวณคนละทาง และไม่มีที่ไหนบนหน้าจอบอกว่าอันไหนคือฐานที่ถูก

## กลไกที่เขาทำได้ดี และเรายังไม่มี

### แผนงาน (Gantt) — ลึกกว่าที่เอกสารสองฉบับแรกบันทึกไว้มาก

- **CPM จริง** ปุ่มคำนวณเส้นวิกฤต ติ๊กงานวิกฤตให้เองจากลำดับงาน และมีคอลัมน์ `TF` (Total Float) ในหน้ารายการงาน
- **โหมดคำนวณวันอัตโนมัติ** ปุ่มบอกสถานะปัจจุบันตรง ๆ ว่า "ตอนนี้ใช้วันที่ท่านพิมพ์เอง — แก้ระยะเวลาต้นน้ำแล้วงานปลายน้ำไม่ขยับตาม"
- **Baseline** เก็บแผนปัจจุบันไว้เทียบ และเปิดเส้นแผนเดิมทับได้
- **WBS หลายระดับ** ปุ่ม Indent/Outdent (Tab/Shift+Tab) ปุ่มลัด F2 F7 F8 และปุ่มเพิ่มงานย่อย/งาน/หมุดหมายรายแถว
- **สเกลเวลา 4 ระดับ** วัน สัปดาห์ เดือน ไตรมาส
- คอลัมน์เงินแยกสี่ช่อง: BUDGET หลัก · BUDGET เพิ่ม · SPEND หลัก · SPEND เพิ่ม
- ปุ่มส่งออกครบแถว: นำเข้า Excel/CSV · Print/PDF · CSV · LINE

### งวดงาน–งวดเงิน — มีเอกสารรายงวดที่เรายังไม่มี

- ปุ่ม **ใบขอเบิก** ต่อหนึ่งงวด คำอธิบายเขียนว่า "พิมพ์ใบขอเบิกงวดนี้ พร้อมช่องลงนาม — ยื่นที่ปรึกษาได้เลย"
  **ข้อนี้ทำให้คำอวดเดิมของเราที่ว่า "คู่แข่งไม่มีเอกสารราชการ" ต้องแก้** เขามีเอกสารรายงวด
  ส่วนที่เรามีและเขาไม่มีคือ **บัญชีงวดงานแนบท้ายสัญญาทั้งชุด พร้อมยอดเป็นตัวอักษร**
- ปุ่ม **แทรกงวดถัดจากนี้** "สัญญาแก้ไขเพิ่มงวดกลางสัญญา — แทรกแล้วเลขงวดถัดไปเลื่อนให้เอง พร้อมย้ายงานที่ผูกไว้"
- ช่อง **อ้างอิงสัญญาแก้ไข / เหตุผลที่แก้งวดนี้** พร้อมคำอธิบาย "แก้งวดงานได้ตลอดเวลา — ช่องนี้ไว้บันทึกว่าแก้ตามเอกสารฉบับไหน เผื่อตรวจย้อนหลัง"
- บล็อกสรุปเงินประกันผลงานท้ายหน้า พร้อม**วันครบกำหนดคืนที่คำนวณจริง** (สิ้นสุดโครงการ 26 ก.พ. 70 → คืน 26 ก.พ. 71)

### ฟอร์มบันทึกจริงต่องวด — ตรงกับ IP-135 ของเราพอดี

หัวข้อในฟอร์ม: **"การเบิกจริง — บันทึกเมื่อยื่นเบิก / ที่ปรึกษารับรอง / เงินเข้า"**
พร้อมประโยคกำกับ: *"ระบบคำนวณ 'เงินรับจริงงวดนี้' ให้แล้ว (ดูในการ์ดงวด) — ช่องนี้ไว้บันทึกตัวเลขที่เกิดขึ้นจริง ซึ่งมักไม่ตรงกัน"*

| ช่อง | หมายเหตุบนหน้าจอ |
|---|---|
| ยอดที่ขอเบิก (บาท) | มีปุ่ม **เติมยอดขอเบิก** เติมยอดที่ระบบคำนวณได้ (ตัวอย่างขึ้น 311,100 บาท) |
| วันที่ยื่นขอเบิก | |
| ยอดที่ที่ปรึกษารับรอง (บาท) | "ต่างจากยอดขอเบิกได้ — ระบบจะแสดงผลต่างให้เห็น" · ตัวอย่างในช่องอธิบายว่า "ขอ 21 ล้าน รับรอง 19 ล้าน ก็กรอกตามจริง" |
| วันที่รับรอง | |
| เงินเข้าจริง (บาท) | "ใช้คู่กับ 'วันที่จ่ายจริง' ด้านบน ขึ้นเป็นเส้นกระแสเงินสดบน S-Curve" |
| วันที่จ่ายจริง | อยู่แยกด้านบนคู่กับ "วันแผน" ไม่ได้อยู่ในกลุ่มการเบิกจริง |
| สถานะ | Planned / Invoiced / Paid เป็นช่องเลือกเอง ไม่ได้อนุมานจากข้อมูล |

**จุดที่ฟอร์มเขาสับสนเอง และเป็นบทเรียนตรงสำหรับเรา:** ปุ่มเติมอัตโนมัติเติมยอด**สุทธิ** 311,100
แต่ข้อมูลตัวอย่างของเขาเองกรอกไว้ 305,000 ทั้งสามช่อง ซึ่งเป็นยอด**มูลค่างานก่อนหัก**
ฟอร์มเดียวจึงปนสองระดับของเงินโดยไม่มีป้ายบอกว่าช่องไหนคือระดับไหน

### Data Date — พฤติกรรมการตัดข้อมูลที่ยืนยันด้วยตัวเลขจริง

- Data Date เป็น **ค่าตั้งระดับแอปทั้งเครื่อง** อยู่ในกล่องตั้งค่า ป้ายว่า `Data Date (วันนี้)` แก้ได้ ค่าเริ่มต้นคือวันจริง
- หัวคอลัมน์เดือนแรกของตารางเขียนกำกับ `ส.ค. 69 (DD 25/08)`
- **เส้นข้อมูลจริงตัดที่ Data Date จริง ไม่ลากต่อ** — เดือนถัดจากวันตัดข้อมูลแสดง `—` ทุกช่องสำหรับ
  ค่าใช้จ่ายจริง มูลค่างานสำเร็จ ยอดขอเบิก ยอดรับรอง และเงินรับจริง ส่วนเส้นแผนลากเต็มถึงจบโครงการ
- หลักฐานที่ชัดที่สุด: งวดที่ 1 มีเงินเข้าจริง 305,000 ลงวันที่ **30 ส.ค. 69** ซึ่งอยู่หลัง Data Date 25 ส.ค.
  ผลคือแถว **เงินรับจริงแสดง ฿0** ขณะที่ยอดขอเบิก (19 ส.ค.) และยอดรับรอง (23 ส.ค.) ขึ้นครบ 305,000
  **เขาตัดตามวันที่ของแต่ละยอด ไม่ใช่ตัดทั้งงวด** — นี่คือรายละเอียดที่สำคัญที่สุดสำหรับ IP-135
- ฐานคิดประกาศใต้กราฟ: `Original = 6,100,000` · `Current Approved / Forecast = 6,710,000`
  และเลือกได้ว่าค่าใช้จ่ายจริงนับ `เฉพาะสัญญาหลัก` หรือ `หลัก + งานเพิ่ม`
- ประโยคใต้กราฟที่ยังยืนเหมือนเดิม: **"มูลค่างานสำเร็จ = เนื้องานจริง (% สำเร็จ × งบกิจกรรม) · เงินรับจริงแสดงเป็นคนละเส้น ไม่ปนกัน"**

### กำลังคน — มีคลังมาตรฐานภาระงานอยู่ข้างใน

กล่องจัดสรรอัตโนมัติให้ตั้ง **ประเภทงานมาตรฐาน + ปริมาณงาน + ทีม** ต่อกิจกรรม
แล้ว "ระบบจะคำนวณกำลังคนตามมาตรฐานภาระงาน แล้วสร้างการมอบหมายให้อัตโนมัติ"

รายการประเภทงานมาตรฐานมีราว **250 รายการ** เป็นชื่อเนื้องานก่อสร้างไทยที่ละเอียดระดับ
`ขุดฐานราก ดินทั่วไป` · `เทคอนกรีตผสมเสร็จ (Pump)` · `Boring Test (ลึก 26-30 ม.)` ·
`ผนังก่ออิฐมวลเบา 20x60x7.5ซม.` · `ระบบกันซึมกันร้อน (7 Layers) หนา 1500 Mic.`

**อนุมาน:** ชุดนี้คือตารางอัตราแรงงานต่อหน่วยแบบเดียวกับที่อยู่ในเอกสารหลักเกณฑ์ราคากลาง
ซึ่งเรามีต้นฉบับใน `km/` อยู่แล้ว จึงทำเองได้จากต้นทางโดยไม่ต้องแตะของเขา

### ทำงานเป็นทีม — กลไกที่เราเหนือกว่าได้จริง

กล่องแชร์โครงการเขียนเองว่า: สร้าง **รหัสใช้งานร่วมกัน 6 หลัก** · **ใครก็ตามที่มีรหัสนี้เข้าถึงและแก้ไขได้**
· ซิงค์อัตโนมัติทุก ~25 วินาที · **"หากแก้ไขพร้อมกัน ระบบจะใช้ของคนที่บันทึกทีหลัง"** · รูปความคืบหน้าไม่ถูกแชร์

> เรามี `organizations` + `organization_members` แยก owner/admin/member/viewer ใน schema แล้ว
> และ "ของคนที่บันทึกทีหลังชนะ" คือการทำข้อมูลหายโดยการออกแบบ ซึ่งเรากันได้ตั้งแต่ต้น

### คลาวด์ — ลงมือทดสอบจริงแล้ว และเจอจุดพังที่เราเคยทำนายไว้ล่วงหน้า

**ทำ:** สร้างรหัสแชร์จริงบนโครงการทดสอบของเราเอง แล้วใช้งานต่ออีกสักพัก

**ได้:**

- รหัสที่ระบบออกให้เป็น **6 หลักผสมตัวอักษรกับตัวเลข** (ตัวอย่างที่ได้: `Y7P9L7`)
- กล่องจัดการการแชร์เขียนว่า **"บทบาทของคุณ: เจ้าของโครงการ"** — แปลว่าเขามีแนวคิดเรื่องบทบาทอยู่ในระบบ
  แต่**ไม่มีที่ไหนให้กำหนดบทบาทของคนที่เข้าร่วม** ข้อความกำกับยังเขียนตรง ๆ ว่า
  "ส่งรหัสนี้ให้เพื่อนร่วมงาน เพื่อเข้าถึงและ**แก้ไข**โครงการนี้ร่วมกัน"
- ยกเลิกการแชร์ได้ และมีกล่องยืนยันก่อนยกเลิก (เรายกเลิกรหัสทดสอบเรียบร้อยแล้ว ไม่ทิ้งลิงก์ค้างไว้)

**จุดพังที่เจอระหว่างทาง และเป็นข้อสำคัญที่สุดของหัวข้อนี้:**

ระหว่างใช้งานต่อเนื่อง แอปขึ้นข้อความว่า

> **`☁ อัปขึ้น cloud ไม่สำเร็จ: JWT expired`**

token ที่ส่งเข้า iframe ผ่าน URL fragment ตอนเปิดแอป **หมดอายุกลางคัน และไม่มีการต่ออายุ**
ผู้ใช้ทำงานต่อได้ตามปกติทุกอย่าง แต่งานไม่ได้ขึ้นคลาวด์อีกแล้ว
พอกดโหลดหน้าใหม่ ระบบออก token ใหม่ให้ แล้วสถานะกลับเป็น `☁ ซิงค์ขึ้น cloud แล้ว` ทันที
ข้อมูลไม่หายเพราะเขาเก็บที่เครื่องเป็นหลัก แต่**สำเนาบนคลาวด์ค้างอยู่ที่เดิมโดยไม่มีอะไรบอกให้รีโหลด**

สองข้อที่ตามมาจากอาการนี้:

1. **ยืนยันข้อ "ห้ามลอก" ที่เราเขียนไว้ตั้งแต่เอกสาร BOQ เมื่อ 24 ส.ค. ว่าอย่าส่ง token ผ่าน URL fragment เข้า iframe**
   ตอนนั้นเราให้เหตุผลว่าสิทธิ์ต้องตัดสินที่เซิร์ฟเวอร์ทุกครั้ง วันนี้เห็นผลของการไม่ทำแบบนั้นด้วยตาแล้ว
   token ที่ยิงเข้าไปครั้งเดียวตอนโหลด ย่อมมีวันหมดอายุระหว่างที่คนยังทำงานอยู่
2. **ข้อความผิดพลาดเป็นศัพท์โปรแกรมเมอร์ดิบ** คำว่า JWT ไม่มีความหมายกับผู้รับเหมาไทย
   ข้อความที่ถูกต้องต้องบอกว่าเกิดอะไรขึ้นและต้องทำอะไรต่อ

### ที่เก็บข้อมูล — ตัวเลขที่เปลี่ยนการตัดสินใจของเรา

กล่องตั้งค่าแสดง `Storage 2.02 MB / ~4.00 MB (50.6%)` ด้วยข้อมูลเพียง 3 โครงการ
พร้อมปุ่มแก้ปัญหาพื้นที่เต็มครบชุด: ย้ายรูปไป IndexedDB และลบ log เก่า · เก็บโครงการที่จบแล้วเข้าคลัง ·
ส่งออกสำรองเป็น JSON · นำเข้าไฟล์สำรอง · ล้างข้อมูลทั้งหมด

**นี่คือคำเตือนตรงต่อการตัดสินใจ IP-135 ของเราที่จะเก็บ workspace ลง localStorage:**
เพดานจริงอยู่ราว 5 MB และเขาชน 50% ตั้งแต่ 3 โครงการ ของเราจึงต้อง (ก) ไม่เก็บรูปใน localStorage
(ข) เก็บเฉพาะโครงการที่กำลังทำ (ค) ถือว่า localStorage เป็นสะพานชั่วคราวไป IP-139 เท่านั้น

### รายละเอียดอื่นที่บันทึกไว้ใช้ทำแผน

- **แม่แบบสร้างอัตโนมัติ 4 ชนิด:** บ้านพักอาศัย 2 ชั้น · อาคารพาณิชย์ 3 ชั้น · ถนน คสล. · รั้วและถมดิน
- **สองตัวเลือกที่แม่แบบของเรายังไม่มี:** ข้ามวันหยุด (อาทิตย์ + นักขัตฤกษ์ไทย) และ เผื่อวันฝน/ความเสี่ยง +5/+10/+15%
- **รายงาน 4 แบบ:** Weekly Status · Look-Ahead 3 สัปดาห์ · EVM Performance · Resource Utilization
  ส่งออก CSV แยก 4 ชุด (Projects / Activities / EVM by WBS / Resources) พร้อมสำรอง JSON และปุ่ม PDF กับ LINE
- **รายงาน LINE** เปิดเป็นกล่องข้อความให้คัดลอกเอง ไม่ใช่คัดลอกลงคลิปบอร์ดเงียบ ๆ
  เนื้อหาเป็นข้อความสั้น มีชื่อโครงการ วันที่ ความคืบหน้า BAC/EAC SPI/CPI จำนวนงาน และรายการงวดเงินทุกงวด
- **สะพานข้ามแอปเป็นไฟล์:** เมนูนำเข้างวดงานจากแอป BOQ ผ่านไฟล์นามสกุลเฉพาะ ยังอยู่
- **หน้าแรกของภาพรวมมีกล่อง "เริ่มที่นี่ — วันนี้ทำอะไร?"** แบ่ง ทำงานประจำวัน / เริ่มโครงการใหม่ / แค่อยากลองดูก่อน
- **กล่องแจ้งเตือน** แบ่ง วันนี้ต้องทำ / พรุ่งนี้ต้องทำ / ภายใน 7 วัน และดึงจุดกำลังคนเกินขึ้นมาเตือน
- ทุกหน้าติดเลขขั้น (ขั้น 5, ขั้น 8) และประโยค "แนะนำ: ทำตามลำดับขั้นจะไม่หลง"
- หน้าที่เป็นผลลัพธ์ล้วนติดป้าย "ดูอย่างเดียว — สรุปจากข้อมูลที่กรอกในขั้น 1–8 โดยอัตโนมัติ"
- แถบบนสุดของแอปพิมพ์คำว่า Data Date ผิดเป็น **"ข้อมูล Date Date = 25 ส.ค. 69 (วันจริง)"**

## ห้ามลอก (เพิ่มจากรายการเดิม)

- **แชร์ด้วยรหัส 6 หลักที่ให้สิทธิ์แก้ไขเต็มกับทุกคนที่ถือรหัส** และ **แก้พร้อมกันแล้วเอาของคนที่บันทึกทีหลัง**
  สองข้อนี้คือการยกสิทธิ์และการทำข้อมูลหายโดยการออกแบบ สิทธิ์ต้องตัดสินที่เซิร์ฟเวอร์และต้องแยกบทบาท
- **ปล่อยค่า undefined ขึ้นหน้าจอ** — ช่องที่ไม่มีค่าต้องมีสภาพว่างที่ตั้งใจ ไม่ใช่ชื่อชนิดข้อมูลของภาษา
- **แจกค่างานจากตัวเลขกลมโดยไม่กระทบยอดกลับหางบสัญญา** — ต้นเหตุของ 2,530,000 เทียบกับ 2,500,000
- **ฟอร์มเดียวปนสองระดับของเงินโดยไม่มีป้าย** — ยอดก่อนหักกับยอดสุทธิต้องบอกให้ชัดทีละช่อง
- **ตัวเลขสรุประดับพอร์ตกับระดับโครงการที่คำนวณคนละทาง** โดยไม่ประกาศฐานคิด
- ชื่อแอป ชื่อเมนู ชื่อโครงการตัวอย่าง และถ้อยคำบนหน้าจอของเขา — ตั้งชื่อเราเองทั้งหมดตามคำสั่งเจ้าของงาน

## ขอบเขตและข้อควรบันทึกเรื่องการเข้าถึง

- ใช้บัญชีของเจ้าของงานตามคำสั่งของเจ้าของงาน เจ้าของงานเป็นผู้ล็อกอิน Google เอง ผู้ช่วยไม่ได้แตะรหัสผ่านหรือ token
- ทำงานบนสำเนาโครงการของเราเอง (`PRJ-2026-001`) และโครงการที่เราสร้างใหม่ (`PRJ-2569-003`)
  ไม่แก้ไขต้นฉบับโครงการตัวอย่างซึ่งระบบกำกับว่าอ่านอย่างเดียว
- การสร้างโครงการและการกดปุ่มต่าง ๆ เป็นการใช้งานตามปกติของสิทธิ์ทดลองที่เปิดไว้แล้ว
- ไม่มีการดาวน์โหลด source code ไม่มีการทดสอบเจาะช่องโหว่ ไม่มี token หรือข้อมูลของผู้อื่นถูกบันทึกลงเอกสารนี้
