## เห็นอะไรบ้าง — สัญญาสิทธิ์การใช้งาน

`GET /api/access?app=boq-building` ตอบเป็น JSON รูปนี้ เมื่อส่ง `Authorization: Bearer <JWT>`

```json
{
  "ok": true,
  "allowed": true,
  "reason": "all-access",
  "status": "trial_active",
  "mode": "full",
  "read_only": false,
  "permissions": {
    "canViewApp": true, "canExploreFeatures": true, "canEditInputs": true,
    "canCalculate": true, "canSave": true, "canExport": true, "canImport": true
  },
  "source": "trial",
  "expires_at": "2026-08-26T17:00:00+00:00",
  "white_label": false
}
```

เรียกโดยไม่ใส่ header เดียวกันนี้ตอบ `{"ok":true,"allowed":false,"reason":"not_signed_in"}`
แปลว่าการยืนยันตัวตนอยู่ที่ Bearer JWT ไม่ได้อยู่ที่ cookie (`document.cookie` ว่างเปล่าทั้ง origin)

โครงสร้างนี้แยก **สามเรื่องออกจากกันได้สะอาด**: สถานะสิทธิ์ (`status`), ระดับการใช้งาน (`mode`
กับ `read_only`) และความสามารถรายอย่าง (`permissions`) โดยมีวันหมดอายุและที่มาของสิทธิ์กำกับ

## เห็นอะไรบ้าง — วิธีส่งสิทธิ์เข้าตัวแอป

หน้า `/boq-building-app` เป็นเปลือกบาง ๆ ที่มี `<header>`, `div#loading`, `div#gate`
และ `iframe#appFrame` ตัวแอปจริงอยู่ใน iframe ที่ `src` มีรูปแบบนี้

```
/boq-building/?build=<hash>#ck_token=<JWT>&ck_email=…&ck_name=…
              &ck_access=all-access&ck_mode=full&ck_source=trial
```

คือส่งทั้ง **token และระดับสิทธิ์** ผ่าน URL fragment เข้า iframe

## เห็นอะไรบ้าง — ตัวแอปถอดปริมาณ BOQ งานอาคาร

คำโปรยของแอปคือ "ทำงานจากโมเดล" และมีแถบขั้นตอน 5 ขั้นบนสุด:
ตั้งโครงการ → สร้างโมเดล → ตรวจโมเดล → ถอดปริมาณรอตรวจ → เอกสารล็อก

สิ่งที่แสดงพร้อมกันบนหน้าจอเดียว **ตอนเปิดโปรเจกต์เปล่าที่ยังไม่มีข้อมูลเลย**

| ส่วน | ปริมาณที่นับได้ |
|---|---|
| แถบขั้นตอนงาน | 5 ขั้น |
| แถบเครื่องมือหลัก | 12 ปุ่ม (ใหม่ เปิด บันทึก Undo Redo Sync Fit โฟกัสโมเดล กริดและระดับ ฯลฯ) |
| Ribbon หมวดงาน | 6 หมวด (โครงสร้าง สถาปัตย์ สุขาภิบาล ไฟฟ้า ระบบต่าง ๆ เบ็ดเตล็ด) |
| ชนิดองค์อาคารใน ribbon โครงสร้าง | ~17 ชนิด จัดเป็น 7 กลุ่ม |
| ชนิดที่ติดป้าย `HOLD` (ยังใช้ไม่ได้) | 8 จาก 17 |
| โหมดแสดงผล | 4 (ผังพื้น รูปด้าน รูปตัด 3 มิติ) |
| Panel อื่นที่เปิดอยู่พร้อมกัน | Tree โครงการ, กริด/ระดับชั้น, Inspector, ตาราง BOM, status bar, ป้าย trial ลอย |
| Modal ที่เด้งทับอยู่หน้าสุด | "อาคารใหม่ 3 คลิก" พร้อมตัวเลือกประเภทอาคาร 9 แบบ |

Panel ตรวจรับโมเดลแยกเป็น 4 หัวข้อ แต่ละหัวข้อมีสถานะและเหตุผลกำกับเป็นประโยค:
ตำแหน่งอ้างอิง (ต้องตรวจ) · พื้นผิวและช่องเปิด (ยังไม่ตรวจ) · ปริมาณเทียบโมเดล (ยังไม่ตรวจ) ·
หลักฐานที่ใช้ (ยังไม่มีใบวัด — "ต้องสร้างใบวัดจากรูปทรงก่อน จึงจะยืนยันความตรงของปริมาณได้")

หัวข้ออ้างอิงโครงการรอ 5 อย่างก่อนล็อกออกเอกสาร: เลขที่แบบ · Revision · Grid · Level ·
ล็อกออกเอกสาร

แอปยังมีชุดเครื่องมือคู่ขนานอีกชุดชื่อ "เครื่องมือ Legacy · ฐานรากเสาเข็ม F1–F16"

## ประเมิน — ทำไมใช้ยาก

**อนุมาน แต่มีหลักฐานหนุนชัด:** ปัญหาไม่ใช่ฟีเจอร์เยอะ แต่เป็น
**โปรเจกต์ว่างเปล่ากลับแสดง UI มากที่สุด** ทั้งจอประกาศคำว่า "ยังไม่มี / ยังไม่ตั้ง / ยังไม่ตรวจ"
รวม 8 จุด พร้อมกับ ribbon ~90 ทางเข้า ที่ครึ่งหนึ่งกดไม่ได้เพราะติด `HOLD`
คนเปิดครั้งแรกจึงไม่มีทางรู้ว่าต้องกดอะไรก่อน

เทียบกับ Estimate-BOQ v2 ที่โปรเจกต์เปล่าแสดงประโยคเดียวว่า "ลากไฟล์ PDF/JPG วางที่นี่"
— ตรงนี้ของเดิมของเราดีกว่าอย่างชัดเจน และไม่ควรแก้

ความต่างเชิงหลักคิดที่สำคัญกว่านั้น: ของเขาบังคับ **สร้างโมเดลก่อน แล้วปริมาณจึงตกออกมา**
ส่วนของเราคือ **อ่านแบบจริงแล้ววัด** วิธีของเราตรงกับลำดับที่ผู้ประมาณราคาทำงานจริง
และไม่บังคับให้ผู้ใช้เรียนโปรแกรมโมเดลลิ่งก่อนได้ผลลัพธ์แรก

**มติของเจ้าของงาน: ไม่นำรูปแบบการใช้งานของแอปนี้มาใช้**

## เก็บมาใช้แค่สามอย่าง

ทั้งสามอย่างไม่เพิ่มศัพท์ใหม่ ไม่เพิ่มหน้าจอ และไม่เพิ่มขั้นตอนให้ผู้ใช้

1. **ป้าย `HOLD` บนฟีเจอร์ที่ยังไม่เสร็จ** — บอกตรง ๆ ว่ายังใช้ไม่ได้ ดีกว่าปล่อยให้กดแล้วเจอของพัง
   ข้อควรระวังจากของเขาเอง: ถ้า `HOLD` มากถึงครึ่งหนึ่งของรายการ ป้ายจะกลายเป็นเสียงรบกวน
   ควรซ่อนหมวดที่ยังไม่มีอะไรใช้ได้เลย แทนการโชว์รายการที่กดไม่ได้ทั้งแถว
2. **เลขที่ build ที่ status bar** — เวลาผู้ใช้แจ้งปัญหา จะรู้ทันทีว่าเขาอยู่รุ่นไหน
3. **ปุ่มเลือกขอบเขตของตาราง BOQ สามปุ่ม** — หน้านี้ / ที่เลือก / ทั้งโครงการ

และอีกหนึ่งอย่างที่อยู่ฝั่ง backend ผู้ใช้มองไม่เห็น จึงไม่กระทบ simple & easy:
**รูปร่าง JSON ของ `/api/access`** ที่แยก `status` / `mode` + `read_only` / `permissions{}`
พร้อม `expires_at` และ `source` — ใส่ลงใน `app_entitlements.limits` (jsonb) ของ ESTIMETR ได้ตรง ๆ
โดยไม่ต้องเพิ่มคอลัมน์

## ห้ามลอก

**ส่ง token และสิทธิ์ผ่าน URL fragment เข้า iframe** — `ck_access=all-access&ck_mode=full`
เดินทางมาทางฝั่ง client ถ้าตัวแอปใน iframe เชื่อค่านี้ ก็เท่ากับให้ผู้ใช้ประกาศสิทธิ์ตัวเอง
เอกสารนี้ **ไม่ได้ทดสอบเจาะ** เพราะเป็นระบบของผู้อื่น จึงบันทึกเป็นข้อสังเกตเชิงโครงสร้างเท่านั้น
สิ่งที่ยึดไว้คือ: สิทธิ์ต้องตัดสินที่ server ทุกครั้งที่มีผลต่อข้อมูลหรือเอกสาร
ค่าที่ client ส่งมาใช้ได้แค่เพื่อแสดงผล

**อนุมาน:** นอกจากเรื่องสิทธิ์ การวาง JWT ใน fragment ยังทำให้ token ไปโผล่ใน history
และอ่านได้จากทุกสคริปต์ใน origin นั้น

รายการอื่นที่ไม่นำมาใช้: workflow ที่บังคับสร้างโมเดลก่อน, ribbon หลายสิบทางเข้า,
โหมดแสดงผล 4 แบบพร้อมกัน, การมีชุดเครื่องมือ Legacy คู่ขนานกับชุดใหม่,
และปุ่มกระโดดข้ามไปแอปอื่นกลางงาน

## ช่องที่ควรปิดในแอปของเราเอง

สองข้อนี้พบตอนรัน AI วิเคราะห์จริงบน `doh-thai.com/estimate/` (หน้า 17 ของ `Attach_TOR_1.pdf`
โครงการโดมอเนกประสงค์โรงเรียนบ้านหนองน้อย จ.สกลนคร) ทั้งสองข้อใช้ข้อมูลที่ AI คืนมาอยู่แล้ว
ไม่ต้องเพิ่มหน้าจอใหม่ และมีค่ามากกว่าทุกอย่างที่ลอกจากแอปอื่นได้

### ข้อ 1 — AI อ่านสเกลได้แล้ว แต่แอปไม่รับไปใช้

**เห็น:** ผลวิเคราะห์ระบุ `ประเภท: แปลนโครงสร้างฐานราก` และ `สเกล: 1:125`
ขณะที่ status bar และแถบเครื่องมือยังขึ้น **"สเกล: ยังไม่ตั้ง"** อยู่เหมือนเดิม

ค่าที่ AI อ่านได้ไม่ได้เชื่อมกับสถานะสเกลของหน้านั้นเลย ผู้ใช้จึงยังต้องไปสอบเทียบด้วยมือ
ทั้งที่ระบบรู้คำตอบแล้ว และขั้น 📐 สเกล เป็นขั้นที่ขัดจังหวะที่สุดของทั้ง flow เพราะเครื่องมือวัด
ทุกตัวถูกล็อกไว้ก่อนจนกว่าจะสอบเทียบเสร็จ

**สิ่งที่ควรทำ**

- ให้ผลวิเคราะห์แสดงแถบเสนอค่าหนึ่งบรรทัดใต้หัวข้อ: `AI อ่านสเกลจากแบบได้ 1:125 — ใช้ค่านี้`
  พร้อมปุ่มยืนยันปุ่มเดียว และทางเลือก `สอบเทียบเอง`
- ค่าที่ยืนยันแล้วต้องบันทึกว่ามาจาก AI ไม่ใช่จากการวัดของคน เพื่อให้ตรวจย้อนได้ว่าปริมาณ
  ชุดนี้อ้างสเกลจากที่ใด
- ห้ามตั้งสเกลให้เองโดยไม่ถาม สเกลผิดทำให้ทุกปริมาณในหน้านั้นผิดตามทั้งหมด
  การยืนยันต้องเป็นการกระทำของคน

**เงื่อนไขที่ต้องเผื่อ:** แบบที่พิมพ์ย่อ/ขยายจากขนาดกระดาษเดิมจะมีสเกลตามที่เขียนไว้ในแบบ
ไม่ตรงกับสเกลจริงบนไฟล์ ข้อความบนปุ่มจึงต้องบอกว่านี่คือ *สเกลที่แบบระบุไว้*
และควรเสนอให้ตรวจกับระยะที่ทราบค่าหนึ่งเส้นก่อนรับ

### ข้อ 2 — AI ไล่ตำแหน่ง grid มาให้แล้ว แต่ไม่มีที่แสดง

**เห็น:** ในหมายเหตุของผลวิเคราะห์มีบรรทัดเหล่านี้

- `ไล่จุด: F2 @ 1A,2A,3A,4A,6A,1B,3B,4B,5B,6B = 10 · F1 @ ริมขอบกลางช่วง = 2`
- `ระยะ Bay spacing 5 ช่วง @ 4.00 ม. รวมเป็น 20.00 ม. ตรงตามมิติรวม`
- `DIMENSION_MISMATCH: grid 5A และ 2B ในแบบไม่ระบุสัญลักษณ์ฐานรากตามแนว grid ปกติ`

คือ AI ให้ **หลักฐานระดับจุด** มาแล้วว่าตัวเลข 10 ฐานมาจากตำแหน่งใดบ้าง และทักเองว่ามีสองจุด
ที่อ่านไม่ลงตัว แต่ทั้งหมดนี้จบลงเป็นข้อความในกล่องหมายเหตุ ไม่มีใครติ๊กรับหรือปฏิเสธได้ทีละจุด
และไม่มีอะไรกันไม่ให้ตัวเลขที่ยังค้างข้อสงสัยไหลเข้า BOQ

**สิ่งที่ควรทำ** — แปลงบรรทัดไล่จุดให้เป็น checklist ติ๊กยืนยัน โดย**ไม่ต้องมี grid editor**

- แต่ละรายการที่ AI ให้ตำแหน่งมา แตกเป็นรายการย่อยตามจุด (`F2 @ 1A`, `F2 @ 2A`, …)
  แสดงเป็นรายการติ๊ก ✓ ผู้ใช้ยืนยันหรือเอาออกทีละจุด และตัวนับปรับตามจำนวนที่ยืนยันจริง
- จุดที่ AI ติดธง `DIMENSION_MISMATCH` ขึ้นสถานะ **ต้องยืนยันก่อน** และ**บล็อกปุ่ม Import to BOQ**
  ของรายการนั้นไว้จนมีคนตัดสิน — ไม่ใช่แค่เตือนแล้วปล่อยผ่าน
- หัวข้อ "อ่านไม่ชัด — ต้องยืนยัน" ที่มีอยู่แล้ว ให้กลายเป็นรายการบล็อกในชุดเดียวกัน
  โดยเฉพาะกรณีที่ AI เดาค่าแทน เช่นที่รอบนี้เขียนว่า
  `ระดับความลึกก้นหลุมฐานรากไม่ระบุในแปลน — ประมาณการที่ 1.50 ม.`
  ค่าประมาณที่ไม่มีใครรับรองต้องไม่ไหลเข้าเอกสารราคาเงียบ ๆ
- ผู้ใช้ไม่ต้องวาดอะไรเลย มีแค่การติ๊ก จึงยังอยู่ในกรอบ simple & easy

ผลข้างเคียงที่ได้ฟรี: จำนวนที่ยืนยันแล้วกลายเป็นหลักฐานที่ตรวจย้อนได้ว่าปริมาณมาจากจุดใดในแบบ
ซึ่งเป็นสิ่งเดียวกับที่ ESTIMETR เรียกว่า **Evidence** ใน `CONTEXT.md`

## ผลต่อ ESTIMETR ใน repo นี้

**อนุมานจากการอ่านโค้ด ไม่ได้รันทดสอบ**

- `takeoff_runs.runner` (`src/db/schema.ts`) เก็บเป็น text และปัจจุบันมีค่าเดียวคือ
  `MANUAL_RUNNER = "manual"` (`src/server/estimeter/takeoff-repository.ts`)
  การเพิ่ม runner ตัวที่สองสำหรับผล AI ทำได้โดยไม่แก้ schema
- `evidence_references` มี `document_id` และ `page_number` อยู่แล้ว จึงรับ "หลักฐานระดับจุด"
  จากข้อ 2 ได้ทันที ส่วนตำแหน่ง grid ยังไม่มีที่เก็บโดยเฉพาะ
- `takeoff_items.review_state` กับ `itemConfirmationBlocker` ทำหน้าที่เดียวกับ
  gate "Import to BOQ" ที่ต้องมีในข้อ 2 อยู่แล้ว
- ยังไม่มีหน้ารวมแอป มีแต่ `src/app/market/[slug]/page.tsx` รายตัว และ `apps` ไม่มีคอลัมน์หมวด
  ถ้าจะทำ catalogue แบบมีหมวด ต้องเพิ่มทั้งสองอย่าง
- `app_entitlements` ผูกกับ organization ขณะที่ marketplace ที่ดูมานับเป็นคน
  ถ้ากลุ่มผู้ใช้หลักเป็นวิศวกรอิสระ ต้องเคลียร์ก่อนว่าสมาชิกเดี่ยวได้ org ปริยายอัตโนมัติหรือไม่
  เพราะกระทบทุก query ที่ตรวจสิทธิ์

## ขอบเขตและข้อควรบันทึกเรื่องการเข้าถึง

- การเข้าใช้ทำผ่านบัญชีของเจ้าของงาน ตามคำสั่งของเจ้าของงาน
- สิทธิ์ทดลองใช้ฟรี 3 วัน ถูกเปิดใช้ในรอบนี้ dialog ระบุว่า **ใช้ได้ครั้งเดียวต่อบัญชี**
  จึงถือว่าสิทธิ์ของบัญชีนั้นถูกใช้ไปแล้ว
- dialog เดียวกันระบุว่าการเริ่มทดลองใช้เท่ากับยอมรับข้อกำหนดการใช้งานและนโยบายความเป็นส่วนตัว
  และถูกกดยอมรับโดยตัวจัดการ dialog อัตโนมัติของ session นี้
- ไม่มีการดาวน์โหลด source code ของแอปผู้อื่น ไม่มีการทดสอบเจาะช่องโหว่
  และไม่มี token หรือข้อมูลโครงการของผู้อื่นถูกบันทึกลงเอกสารนี้
