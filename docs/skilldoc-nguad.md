## กฎที่เจ้าของงานกำหนด

> ถ้าค่าในตารางที่ 2 มีหลายงวด ก็จะดันลงมาเรื่อย ๆ และเมื่อถึงขอบเขตก็ตัดไปขึ้นหน้าใหม่
> โดยที่หน้าใหม่ก็ต้องมีหัวตารางแบบด้านบนเหมือนกันด้วย จนกว่าจะหมดงวดงานถึงไปเป็นข้อ 3

แตกเป็นข้อบังคับได้ห้าข้อ

| # | กฎ | ทำไม |
|---|---|---|
| 1 | แถวงวดไหลลงมาตามลำดับจนสุดพื้นที่พิมพ์ของหน้านั้น | เอกสารราชการอ่านจากบนลงล่างตามลำดับ ห้ามสลับเพื่อให้หน้าดูเต็ม |
| 2 | ถึงขอบแล้วตัดขึ้นหน้าใหม่ **ห้ามตัดกลางแถว** | งวดที่ขาดครึ่งอยู่คนละหน้าคือยอดเงินที่ผู้ตรวจอ่านไม่ออกว่าของงวดไหน |
| 3 | ทุกหน้าที่ตารางไปโผล่ ต้องมีหัวตารางของตัวเอง | ตารางที่ไม่มีหัวคอลัมน์คือตัวเลขสี่คอลัมน์ที่ไม่มีใครรู้ว่าคอลัมน์ไหนคืออะไร |
| 4 | แถวรวมทั้งสิ้นอยู่กับชิ้นส่วนสุดท้ายเสมอ และมีอันเดียวทั้งฉบับ | ยอดรวมที่ซ้ำหรือลอยอยู่คนละที่กับตารางคือยอดที่ตรวจย้อนไม่ได้ |
| 5 | ข้อ 3 หมายเหตุ ไม่ขึ้นก่อนงวดสุดท้ายจบ | หัวข้อถัดไปที่แทรกกลางตารางทำให้เอกสารอ่านเป็นคนละเรื่อง |

**ข้อ 4 มีกรณีขอบที่ต้องระวัง** ถ้าหน้าสุดท้ายใส่แถวงวดจนเต็มพอดีแล้วแถวรวมไม่เหลือที่
แถวรวมจะถูกยกไปหน้าถัดไป **พร้อมหัวตาราง** ไม่ปล่อยให้ยอดรวมลอยอยู่โดยไม่มีคอลัมน์กำกับ

## ทำไมต้องคำนวณเอง ไม่ปล่อยให้เบราว์เซอร์แบ่งหน้า

เบราว์เซอร์แบ่งหน้าให้เองได้ตอนพิมพ์ ด้วย `break-inside: avoid` และ `display: table-header-group`
แต่มันทำเฉพาะตอนพิมพ์ ตัวอย่างบนหน้าจอจะไม่รู้เรื่องนี้เลย ผลคือสิ่งที่ผู้ใช้อนุมัติบนจอ
ไม่ใช่สิ่งที่ออกมาจากเครื่องพิมพ์ ซึ่งเป็นข้อผิดพลาดที่ค้นพบตอนตรวจ v0.55.0

ระบบนี้จึงวัดความสูงจริงของทุกบล็อกก่อน แล้วตัดสินเองว่าอะไรอยู่หน้าไหน ตัวอย่างกับ PDF
จึงเป็นสิ่งเดียวกันเพราะมาจากผลการคำนวณชุดเดียวกัน

## กลไก

**หนึ่ง — วัดก่อน** เอกสารทั้งฉบับถูกเรนเดอร์ลงกล่องที่มองไม่เห็น (`.doc-measure`) ซึ่งกว้าง
เท่าพื้นที่พิมพ์จริง แล้ววัดทีละชิ้น ทุกแถวของตารางมี `data-row` ส่วนหัวและท้ายตารางมี
`data-part` การวัดรอเสมอจนกว่า `document.fonts.ready` จะผ่าน เพราะความสูงที่วัดด้วย
ฟอนต์สำรองไม่ใช่ความสูงจริง

**สอง — ตัดสิน** `paginate()` รับความสูงเป็นตัวเลขล้วน ไม่แตะ DOM จึงทดสอบได้โดยไม่ต้องมีเบราว์เซอร์
ตารางงวดเข้ามาเป็นบล็อกชนิด `rows` ซึ่งเป็นชนิดเดียวที่แตกข้ามหน้าได้

```ts
{ kind: "rows", id: "milestones", headerHeight, footerHeight, rows: [{ id, height }] }
```

**สาม — ประกอบกลับ** แต่ละหน้าเรนเดอร์ชิ้นส่วนที่ได้รับ ชิ้นส่วนตารางถูกประกอบเป็น `<table>`
ที่มี `<thead>` ของตัวเองเสมอ และมี `<tfoot>` เฉพาะชิ้นสุดท้าย

**สี่ — คอลัมน์ต้องกว้างเท่ากันทุกชิ้น** `table-layout: fixed` พร้อม `colgroup` กำหนดความกว้าง
ทุกคอลัมน์ ถ้าปล่อยให้เบราว์เซอร์คิดใหม่จากเนื้อหาของแต่ละชิ้น จะได้คอลัมน์คนละความกว้าง
ในหน้าคนละหน้า ซึ่งอ่านเหมือนเอกสารคนละฉบับ

## ที่ของแต่ละหน้าคิดอย่างไร

```
พื้นที่พิมพ์ต่อหน้า = 297 − 15 (ขอบบน) − 15 (ขอบล่าง) = 267 มม.
งบที่เนื้อหาใช้ได้   = 267 − ที่ของเลขหน้า (1.6 มม.) = 265.4 มม.
```

เลขหน้ากินแค่ 1.6 มม. เพราะมันล้ำลงไปในขอบล่าง 5 มม. ตัวเลขนี้ไม่ได้ฝังไว้ในโค้ด
แต่วัดจากความสูงบวกระยะขอบล่างตามจริง

## สิ่งที่ยังไม่รองรับ

- **แถวเดียวที่สูงเกินหนึ่งหน้า** เกิดได้ถ้ารายการงานในงวดนั้นยาวมากจนแถวสูงเกิน 265 มม.
  ระบบจะวางแถวนั้นแล้วรายงานผ่าน `overflowing` ซึ่งหน้าจอเอาไปขึ้นคำเตือน ไม่ตัดทิ้งเงียบ ๆ
  แต่แถวนั้นจะล้นออกนอกกรอบกระดาษจริง ทางแก้คือลดข้อความในงวดนั้น
- **ไม่มีการทำให้หน้าสุดท้ายไม่โดดเดี่ยว** ถ้าเหลืองวดเดียวตกไปหน้าใหม่ ระบบไม่ย้ายงวดก่อนหน้า
  ตามไปเป็นเพื่อน เพราะการทำแบบนั้นคือการเปลี่ยนตำแหน่งของงวดที่ผู้ใช้ไม่ได้สั่ง
