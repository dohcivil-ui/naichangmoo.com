# Hermes 24/7 — ธุรกิจบริการ setup ระบบผู้ช่วยตาม request และ use case แรก

**บันทึกจากเจ้าของงาน 2026-08-27** — เก็บไว้ก่อนถึงเฟส 6 ตาม `docs/roadmap/DIRECTION.md`
สถานะ: วิสัยทัศน์ที่บันทึกแล้ว ยังไม่เริ่มสร้าง ต้องผ่าน `/grill-with-docs` และ ADR ใหม่ก่อนเขียนโค้ด

## นิยามใหม่ของ Hermes 24/7

Hermes 24/7 เป็น**บริการรับ setup ระบบผู้ช่วยอัตโนมัติให้องค์กร บริษัท ห้างร้าน และเจ้าของกิจการ
ตาม request** — แต่ละงานต้อง design ตามรูปแบบที่ลูกค้าต้องการ ไม่ใช่ผลิตภัณฑ์สำเร็จรูปกล่องเดียว

- ช่องทางรับงาน: หน้า `/enterprise` (enterprise quotation intake ตาม ADR 0005)
- ปากทางบนหน้าแรก: ช่อง Hermes บน Landing มีปุ่มส่ง use case ชี้เข้าหน้าใบเสนอราคา
- ทุกงานที่รับ: ออกแบบระบบเฉพาะงาน และเขียนบันทึกการออกแบบ (ADR ของระบบนั้น) ก่อนเริ่มสร้างเสมอ
- หมวดสิทธิ์ในทะเบียน: `agent_service` ("ผู้ช่วยทำงาน 24/7") ซึ่งมีอยู่แล้วใน `AppAccess`
- ตำแหน่งในแผนใหญ่: เฟส 6 — เริ่มเมื่อเดโมครบ มีสมาชิก และระบบขึ้น VPS แล้ว

## Use case แรก: ระบบรับบิล-จ่ายบิลของบริษัทรับเหมา

เส้นทางข้อมูลที่เจ้าของงานกำหนด:

1. **รับเอกสารเข้า** — สลิปเงินโอนจากธนาคาร · บิลลายมือที่สแกนมา · ใบกำกับภาษีที่สแกนเป็น PDF ·
   ใบกำกับภาษีอิเล็กทรอนิกส์
2. **OCR อ่านไฟล์** แปลงเป็นรายการรับหรือจ่ายพร้อมจำนวนเงินและคู่ค้า
3. **แยกรายโครงการ** — จับรายการเข้าโครงการที่ถูกต้องของบริษัท
4. **บันทึกเข้า Google Sheet** แยกรายรับ รายจ่าย แยกรายโครงการ
5. **สรุปยอดตามตาราง**
   - สรุปประจำวัน ตามเวลาที่กำหนด
   - สรุปรายสัปดาห์ ตามเวลาที่กำหนด
   - สรุปรายเดือน ตามเวลาที่กำหนด
   - สรุปปิดยอดโครงการเมื่องานจบ

## ข้อที่ต้องตัดสินก่อนเขียนโค้ด (ยกไปรอบ grill ของเฟส 6)

| เรื่อง | ทำไมต้องเคาะ |
|---|---|
| ADR ใหม่แยก "Hermes รับจ้างองค์กร" ออกจาก "Hermes ผู้ตรวจในแพลตฟอร์ม" | ADR 0004 ห้าม Hermes เขียนข้อมูลธุรกิจ แต่ use case นี้เขียน Google Sheet ของลูกค้าโดยตรง ขอบเขตคนละใบ ต้องมีเจ้าของคำแถลงคนละฉบับ |
| เงินผ่านระบบเราเป็น BigInt satang เสมอ | กติกายืนของโปรเจกต์ — ตัวเลขจาก OCR ต้องมีขั้นตรวจโดยคนตาม IP-052 ก่อนลงบัญชี |
| สิทธิ์เข้าถึง Google Sheets ของลูกค้า | ต้องใช้ OAuth ของลูกค้าเอง ไม่ใช่ credential กลางของเรา และบันทึกว่าใครอนุญาตอะไรเมื่อไหร่ |
| ราคาและรอบเก็บเงินของงาน setup | เป็นงานออกแบบรายลูกค้า ราคาต่องานผ่านใบเสนอราคา ไม่ใช่ราคาหน้าเว็บ |
| ความผิดพลาดของ OCR กับบิลลายมือ | ต้องมีคิวตรวจของคน ไม่ใช่ลงบัญชีอัตโนมัติทั้งหมด — ตัวเลขเงินผิดหนึ่งตัวคือความเชื่อที่เสียทั้งระบบ |

## สิ่งที่มีอยู่แล้วและนำมาใช้ต่อได้

- `/enterprise` + `enterprise_quotation_requests` (ADR 0005) — ช่องรับ requirement พร้อม consent
- `agent_service` ในทะเบียนแอปและป้ายสิทธิ์
- แผน Redis queue + worker container ของ IP-176 — โครงเดียวกับที่งานสรุปยอดตามเวลาต้องใช้
- ประสบการณ์ OCR จากงาน ว809 (IP-052, IP-161) — บทเรียนเรื่องขั้นตรวจโดยคนใช้ซ้ำได้ตรง ๆ
