# ADR 0006: The ESTIMETR trial clock starts at explicit activation

**Status:** Accepted

Supersedes the trial start point defined in ADR 0003. Everything else in ADR 0003 stands.

## Context

นายช่างหมูมีการตรวจสิทธิ์สองด่านที่แยกกัน และ `PROJECT.md` ข้อ 1 เขียนไว้ว่าแต่ละ app ประเมิน entitlement
*หลัง* authentication:

- **ด่าน 1 — Platform Membership.** ตัวตนกลางที่เกิดทันทีหลังลงทะเบียน ใช้ตรวจสิทธิ์ของทุก app
  ไม่ผูกกับเวลาและไม่หมดอายุ
- **ด่าน 2 — App Entitlement.** สิทธิ์ของสมาชิกต่อ app หนึ่ง app ซึ่งมีระดับการใช้และข้อจำกัดของตัวเอง
  สำหรับ ESTIMETR คือสิทธิ์ทดลองใช้ 5 วัน 1 โครงการ ปิด export และ print

ADR 0003 ตัดสินว่า `starts_at = member.created_at` และปฏิเสธทางเลือก "เริ่ม trial เมื่อสร้างโครงการแรก"
ด้วยเหตุผลว่า "ไม่สอดคล้องกับเป้าหมายสมาชิก platform ตั้งแต่ registration" เหตุผลนั้นเอาเป้าหมายของด่าน 1
มาตัดสินเรื่องของด่าน 2 ทั้งที่สองอย่างไม่ขัดกัน: สมาชิกเป็นสมาชิกตั้งแต่วันสมัครได้ โดยที่นาฬิกาทดลองใช้
ของแอปยังไม่เริ่มนับ

ผลที่เกิดขึ้นจริงจากการปนสองด่านนี้ไม่ใช่เรื่องทฤษฎี สมาชิกที่สมัครวันนี้แล้วเปิด ESTIMETR ครั้งแรกในวันที่ 6
จะเห็นหน้า "สิทธิ์ทดลองใช้หมดอายุ อ่านได้อย่างเดียว" ทั้งที่ยังไม่เคยกดอะไรในแอปเลย เขาได้ทดลองใช้ศูนย์วัน
จากสิทธิ์ที่ตั้งใจให้ห้าวัน และระบบยังไม่มีที่ไหนบันทึกว่าเขายอมรับเงื่อนไขของสิทธิ์ทดลองใช้เมื่อไร

การเปลี่ยนจุดเริ่มนาฬิกาเป็นการตัดสินใจที่กลับยากเมื่อมีผู้ใช้จริงแล้ว เพราะต้องไปแก้ข้อมูลสิทธิ์ของลูกค้า
จึงบันทึกเป็น ADR ก่อนลงมือ

## Decision

นาฬิกาทดลองใช้ของ ESTIMETR **เริ่มนับเมื่อสมาชิกกดเริ่มทดลองใช้อย่างชัดแจ้ง** ไม่ใช่เมื่อสมัครสมาชิก
และไม่ใช่เมื่อเปิดหน้าแอป

1. **ด่าน 1 (ตอนเข้าใช้งานครั้งแรก):** สร้าง personal organization และ membership แบบ idempotent
   ไม่มีการออก entitlement และไม่มีนาฬิกาใด ๆ เริ่มเดิน
2. **ด่าน 2 (ตอนกดเริ่มทดลองใช้):** สร้างแถวใน `app_entitlements` ด้วย `state = trial`,
   `starts_at = <เวลาที่กด>`, `ends_at = starts_at + 5 days`, `limits` ตาม ADR 0003
   และเขียน audit event `entitlement.trial_activated` ที่ระบุว่าใครกดยอมรับเงื่อนไขเมื่อไร
3. **"ยังไม่เริ่มทดลองใช้" แทนด้วยการไม่มีแถว entitlement** ไม่ใช่ด้วยค่าสมมติใน `starts_at`
   สถานะที่ระบบคำนวณจากภาวะนี้ชื่อ `not_activated` (อ่านได้ สร้างและแก้ไขไม่ได้ `projectLimit = 0`)
4. **การอ่านสิทธิ์ต้องไม่เขียนฐานข้อมูล** `getEstimeterAccess` เป็น read path ล้วน การออกสิทธิ์เกิดจาก
   server action ที่ผู้ใช้กดเท่านั้น
5. **UI ต้องแสดงเงื่อนไข 5 วัน / 1 โครงการ / ปิด export และ print ก่อนปุ่มเริ่มทดลองใช้** เพื่อให้การกด
   เป็นการยอมรับเงื่อนไขที่ผู้ใช้เห็นแล้ว
6. **สิทธิ์ทดลองใช้ผูกกับ organization หนึ่งครั้ง** unique index `(organization_id, app_id)`
   บังคับข้อนี้อยู่แล้ว การกดซ้ำไม่ต่อเวลาและไม่สร้างแถวที่สอง

ส่วนที่ **ยังใช้ตาม ADR 0003 ทั้งหมด ไม่แตะ**: ระยะเวลา 5 วัน, เพดาน 1 โครงการ, `export_enabled = false`,
`print_enabled = false`, การเปลี่ยนเป็น `expired_read_only` เมื่อหมดอายุพร้อม read-only retention,
การบังคับ policy ฝั่ง server ทุก mutation, และ entitlement ของแอปอื่น (`member_free`, `doh_staff_only`)

## Alternatives considered

| Alternative | Why not selected now |
|---|---|
| คงตาม ADR 0003 (`starts_at = member.created_at`) | สมาชิกที่เข้าแอปช้ากว่า 5 วันได้ทดลองใช้ศูนย์วัน และไม่มีบันทึกว่าเขายอมรับเงื่อนไขเมื่อไร |
| เริ่มนับเมื่อเปิดแอปครั้งแรก (implicit) | คนที่เข้ามาดูหน้าจอแล้วปิดไปเสียวันทดลองใช้ฟรีโดยไม่ได้ตัดสินใจ และยังเป็นการตัดสินใจแทนผู้ใช้ |
| เริ่มนับเมื่อสร้างโครงการแรก | ไก่กับไข่ เพราะเพดาน 1 โครงการถูกตรวจจาก entitlement ที่ยังไม่มี และเป็นการเริ่มสิทธิ์โดยผู้ใช้ไม่รู้ตัว |
| เก็บแถว entitlement ไว้ล่วงหน้าโดยใส่ `starts_at` เป็นวันในอนาคตไกล ๆ | ไม่ต้อง migration เหมือนกัน แต่ทำให้ข้อมูลในตารางโกหก คนอ่านตารางจะเข้าใจว่าสิทธิ์จะเริ่มวันนั้นจริง |
| เพิ่มค่า `not_activated` ลง enum `entitlement_state` | ต้อง migration ทั้งที่ภาวะนี้อนุมานได้จากการไม่มีแถวอยู่แล้ว เก็บไว้พิจารณาถ้าวันหนึ่งต้องบันทึกว่าเคยถูกเสนอสิทธิ์แล้วปฏิเสธ |

## Consequences

- **ไม่มี schema change และไม่มี migration** ใช้ `app_entitlements.starts_at` / `ends_at`
  และ unique index `(organization_id, app_id)` ที่ migration 0000 สร้างไว้แล้ว
- **Read path สะอาดขึ้น** การเปิดหน้า ESTIMETR ไม่เขียนฐานข้อมูลอีก ซึ่งปิดความเสี่ยงที่บันทึกไว้
  ใน handoff ของ v0.13.0 ว่า GET request มีการเขียนข้อมูล
- **สถานะที่ UI ต้องรองรับเพิ่มหนึ่งสถานะ** `not_activated` ต้องมีข้อความและ primary action ของตัวเอง
  แยกจาก `not_started` ซึ่งหมายถึงสิทธิ์ที่มีวันเริ่มในอนาคต
- **ข้อจำกัดที่ยอมรับไว้:** สิทธิ์ทดลองใช้ผูกกับ organization ผู้ที่สมัครด้วยอีเมลใหม่ยังได้ทดลองใช้รอบใหม่
  ซึ่งเป็นข้อจำกัดเดียวกับของเดิม ไม่ได้แย่ลง การกันเรื่องนี้จริงจังต้องผูกกับการยืนยันตัวตน
  ซึ่งอยู่นอกขอบเขต ADR นี้
- **ข้อมูลเดิม:** แถว entitlement ที่ออกด้วยนาฬิกาแบบเก่าต้องถูกลบเพื่อให้บัญชีกลับไปอยู่สถานะยังไม่เริ่ม
  ฐานข้อมูลตอนนี้เป็น dev ล้วนและผู้ใช้ยืนยันว่าไม่มีข้อมูลลูกค้าจริง จึงไม่ต้องมี approval record
  ถ้าทำภายหลังตอนมีผู้ใช้จริง การลบสิทธิ์ของลูกค้าต้องมีการอนุญาตที่บันทึกไว้ตาม AGENTS.md
- **การทดสอบ:** เคสที่ยืนยันว่า trial อนุมานจาก `users.created_at` ใช้ไม่ได้อีก แทนด้วยเคสที่ยืนยันว่า
  บัญชีที่ยังไม่กดคือ `not_activated`, การอ่านสิทธิ์ไม่เขียนฐานข้อมูล, การกดสองครั้งได้แถวเดียว
  และนาฬิกาเริ่มที่เวลาที่กด
- **ถ้าจะเปลี่ยนกลับ** ต้องเขียน ADR ใหม่และต้องตอบให้ได้ว่าจะจัดการกับสมาชิกที่กดเริ่มไปแล้วอย่างไร
