# ADR 0024: ปริมาณเก็บว่าได้มาอย่างไร ไม่เก็บคำตัดสินว่าแม่น

**Status:** Accepted — เจ้าของงานเคาะ 2026-09-02 และยืนยันรูปตาราง 2026-09-03 (IP-232 IP-233 IP-234)

## Context

ESTIMETR กำลังจะมีปริมาณจากสามทางที่ความคลาดเคลื่อนไม่เท่ากันไหลเข้าตารางเดียวกัน —
คนพิมพ์ตัวเลขจากแบบในฟอร์ม · คนชี้จุดบนแบบในหน้าวาด (เมาส์ ปากกาบนแท็บเล็ต หรือนิ้วบนมือถือ) ·
และในอนาคต โมเดลอ่านแบบแล้วเสนอ เจ้าของงานทักไว้ใน handoff 2026-09-02 หัวข้อเจ็ดว่า
*"ปริมาณจากสองทางนี้ปนกันในใบเดียวโดยไม่บอกที่มาไม่ได้ ... วันหนึ่งจะไม่มีใครบอกได้ว่าเลขไหน
ตรวจสอบย้อนกลับได้"*

ทางที่ตรงที่สุดคือใส่คอลัมน์ `source: "ai" | "human"` หรือคะแนนความน่าเชื่อถือ แล้วให้ตารางกับ
เอกสารพิมพ์แยกตามนั้น รีโปนี้มีตัวอย่างของทางนั้นอยู่แล้ว — `boq_items.match_confidence`
(schema.ts) เก็บคำตัดสินว่าคู่ที่จับได้น่าเชื่อแค่ไหนไว้เป็นคอลัมน์

แต่เจ้าของงานเสริมทันทีว่า *"สักวันอาจทำให้แม่นเท่ากันได้เมื่อ AI ฉลาดขึ้น"* และสั่งว่า
**"ให้เก็บว่าปริมาณนั้นได้มาอย่างไร ไม่ใช่ตีตราว่าแม่นหรือไม่แม่น ... วันที่ AI เก่งพอจึงแก้แค่เกณฑ์
ไม่ต้องแก้โครงสร้างข้อมูลและไม่ต้องย้ายข้อมูลเก่า"** ข้อนี้เปลี่ยนวิธีออกแบบ ไม่ใช่แค่ความหวัง —
คอลัมน์ `source: "ai"` ที่มีความหมายแฝงว่าแม่นน้อย คือการฝังคำตัดสินของวันนี้ไว้ถาวรในทุกแถว
และกลายเป็นหนี้ทันทีที่คำตัดสินนั้นเปลี่ยน เพราะไม่มีใครรู้ว่าแถวไหนถูกตัดสินด้วยเกณฑ์รุ่นไหน

## Decision

1. **ข้อเท็จจริงเป็นคอลัมน์ คำพิพากษาเป็นฟังก์ชัน** `takeoff_measurements` เก็บ
   `method` (วิธีที่ตัวเลขถูกผลิต) `proposal_id` (ข้อเสนอที่ค่านั้นมาจาก ถ้าโมเดลเสนอ) และ
   `method_context` (ข้อเท็จจริงประกอบที่วัดได้ เช่นชนิด pointer และ calibration ที่ใช้) ·
   **ไม่มีคอลัมน์ไหนเก็บระดับความเชื่อถือ** · คำถามว่าวิธีไหนต้องกำกับที่มาให้เห็นในตารางและ
   เอกสารพิมพ์ ตอบโดย `methodNeedsDisclosure()` ใน `src/lib/quantity-provenance.ts` ซึ่งเป็น
   **ที่เดียวที่ต้องแก้วันที่เกณฑ์เปลี่ยน** ไม่มี migration ไม่ต้องย้ายข้อมูล

2. **ค่าของ `method` เป็นข้อเท็จจริงล้วน ไม่มีค่าไหนแปลว่าแม่นหรือไม่แม่น** ทะเบียนวันนี้:
   `typed` คนอ่านจากแบบแล้วพิมพ์ · `pointer` คนชี้จุดบนแบบ · `pointer_count` คนแตะนับ ·
   `region_trace` โค้ดไล่ขอบห้องเสนอ คนดูรูปแล้วยืนยัน · `model` โมเดลเสนอ คนกดรับ ·
   ทะเบียนอยู่ในโค้ด ฐานเก็บค่า (รูปทรงเดียวกับ `platform_channels`) และเทสต์เฝ้าว่า
   **ทะเบียนห้ามมีช่องชื่อ confidence, score, trust หรือทำนองนั้น**

3. **อุปกรณ์ไม่ได้อยู่ใน `method`** งานพิมพ์เลขจากแบบบนเดสก์ท็อปกับบนมือถือเป็น `typed`
   เหมือนกัน เพราะเป็นวิธีเดียวกันจริง (เจ้าของงานยืนยันว่าสี่งานบนมือถือแม่นเท่าเดสก์ท็อป)
   ชนิดอุปกรณ์เป็นข้อเท็จจริงใน `method_context` ซึ่งอ่านได้เมื่อวันหนึ่งอยากถาม แต่ไม่ได้
   ตัดสินอะไรวันนี้

4. **ค่าจากโมเดลต้องย้อนถึงรุ่นโมเดลและคนที่กดรับได้ระดับโครงสร้าง ไม่ใช่ระดับวินัย**
   CHECK `takeoff_measurements_model_pairs_proposal`: `(method = 'model') = (proposal_id IS NOT NULL)`
   บังคับสองทิศ — ค่าจากโมเดล**ต้อง**ชี้ `assistant_proposals` (ซึ่งเก็บ `model_id` ของรุ่นที่ตอบจริง
   แม้สลับค่ายสำรอง `decided_by` `decided_at` ครบตาม ADR 0019) และค่าที่ไม่ใช่โมเดล**ห้าม**ชี้
   เพราะทิศเดียวยังเหลือช่องให้เอาค่าที่เดามาแปะ `typed` แล้วแนบข้อเสนอของงานอื่น ·
   `ON DELETE RESTRICT` ห้ามลบข้อเสนอที่มีปริมาณอ้างอยู่ · ไม่ลอกช่องของ `assistant_proposals`
   มาซ้ำในตารางนี้ เพราะสำเนาคือของที่วันหนึ่งจะขัดกับต้นฉบับ

5. **`method` ไม่มี DEFAULT** ทุกเส้นทางเขียนต้องประกาศวิธีเอง ผลที่เกิดจริงตอนทำ migration 0015:
   typecheck จับได้ทันทีว่า `addItemMeasurement` ยังไม่ประกาศ ซึ่งคือสิ่งที่ต้องเกิด — ค่าตั้งต้น
   คือวิธีที่เส้นทางใหม่ในอนาคตจะติดป้ายผิดโดยไม่มีใครรู้ · แถวเดิมทั้งหมด backfill เป็น `typed`
   ซึ่งเป็นข้อเท็จจริง (ทุกแถวมาจากฟอร์มพิมพ์มือ) ไม่ใช่ค่าแทนที่

6. **สเกลของหน้าใช้หลักเดียวกัน** `drawing_calibrations.method` เก็บว่าสเกลถูกตั้งด้วยการคลิก
   สองจุด (`two_point`) หรือจากระยะที่แบบเขียนซึ่งเกาะแนวเสา (`stated_dimension`) —
   วันที่ตัวเลขทั้งหน้าน่าสงสัย คำถามแรกคือสเกลมาจากไหน · และ `confirmed_by NOT NULL`
   ทำให้ไม่มีเส้นทางไหน แม้แต่ SQL มือ ที่สเกลลงฐานได้โดยไม่มีชื่อคน (ADR 0019 + IP-052
   กลายเป็นโครงสร้าง)

7. **แถวที่มาจากการวาดเก็บผลลัพธ์ ส่วนตัวประกอบของมันคือเรขาคณิตในหลักฐาน**
   กติกาเดิมของ `takeoff_measurements` คือหน่วยกำหนดจำนวนมิติ (ตร.ม. ต้องมีกว้าง × ยาว)
   ซึ่งถูกต้องสำหรับแถวที่คนพิมพ์ เพราะสองตัวประกอบนั้นคือสิ่งที่คนอ่านจากแบบจริง ๆ
   แต่รูปหลายเหลี่ยมที่ไล่จากแบบไม่มีกว้าง × ยาว มันมีจุดยอดหกจุดกับพื้นที่หนึ่งค่า
   การบังคับให้แยกเป็นสองตัวคูณคือการประดิษฐ์ตัวเลขที่ไม่มีอยู่จริง จึงขยายกติกา:
   **แถวที่ `method` เป็น `pointer` หรือ `region_trace` และหน่วยเป็นพื้นที่ เก็บมิติเดียวคือพื้นที่**
   โดยจุดยอดทั้งหมดพร้อมสเกล ณ ตอนยืนยันอยู่ใน `evidence_references.geometry` ·
   สี่เหลี่ยมยังเก็บกว้าง × ยาว เพราะมันมีจริง · แถวที่คนพิมพ์กติกาเดิมทุกประการ

## Alternatives considered

| ทางเลือก | ทำไมไม่เลือกตอนนี้ |
|---|---|
| คอลัมน์ `source: "ai" \| "human"` | ฝังคำตัดสินสองค่าของวันนี้ไว้ถาวร วันที่ AI เก่งพอต้อง migrate ทุกแถวและไม่มีใครรู้ว่าแถวไหนตัดสินด้วยเกณฑ์รุ่นไหน — คือหนี้ที่เจ้าของงานสั่งห้ามก่อไว้ตรง ๆ |
| คอลัมน์คะแนนความเชื่อถือ แบบ `boq_items.match_confidence` | ตัวอย่างในรีโปนี้เองว่าคำพิพากษาเป็นคอลัมน์แล้วแก้ไม่ได้ · เกณฑ์ที่ใช้ให้คะแนนไม่ได้ถูกเก็บไว้ข้าง ๆ คะแนน จึงตีความย้อนหลังไม่ได้ |
| ลอก `model_id` `decided_by` มาไว้ใน `takeoff_measurements` | สำเนาของ `assistant_proposals` ที่วันหนึ่งขัดกับต้นฉบับ (เช่น failover เปลี่ยน `model_id` หลังจอง) · foreign key + CHECK ให้สิ่งเดียวกันโดยไม่มีสำเนา |
| ใส่ `device` เป็นค่าหนึ่งใน `method` (เช่น `touch_typed`) | ทำให้งานเดียวกันมีสองชื่อ และแอบตีตรามือถือว่าเป็นคนละเกรด ซึ่งเจ้าของงานปฏิเสธเอง · อุปกรณ์เป็นข้อเท็จจริงประกอบ ไม่ใช่วิธี |
| บังคับ CHECK ทิศเดียว (model ⇒ proposal) | เหลือช่องให้ค่าที่ไม่ใช่โมเดลแนบข้อเสนอของคนอื่นมาเป็นร่องรอยปลอม |
| แยกรูปหลายเหลี่ยมเป็นกว้าง × ยาวสมมติ เพื่อรักษากติกาหน่วยเดิม | ประดิษฐ์ตัวเลขสองตัวที่ไม่มีบนแบบ — ตรงข้ามกับเหตุผลที่ตารางนี้มีอยู่ ("nobody can tell whether 12.5 cu.m came from the right footing") |

## Consequences

**Operational** ตารางถอดปริมาณต้องแสดงป้ายวิธีทุกแถวจากทะเบียน (`QUANTITY_METHODS[method].label`
ภาษาไทย ตาม G14) · เอกสารพิมพ์ต้องแยกวิธีที่ `methodNeedsDisclosure()` ตอบว่าต้องกำกับ —
หน้าที่นี้ตกที่ท่อ `document_releases` ซึ่งยังไม่มี (IP-109) บันทึกไว้ในแผน ไม่ทำในรอบนี้

**Security** ค่าจากโมเดลเข้าฐานไม่ได้เลยถ้าไม่มีแถว `assistant_proposals` ที่ผ่าน `settleProposal`
— ADR 0019 ข้อ 1 ("ไม่มีเส้นทางไหนให้ค่าจากโมเดลอยู่ในข้อมูลผู้ใช้โดยไม่มีคนกด") ได้ด่านที่ฐานข้อมูล
บังคับเพิ่มจากด่านในโค้ด

**Cost** ศูนย์ ไม่มีบริการภายนอก

**Migration** `drizzle/0015_harsh_cobalt_man.sql` — เพิ่มสามคอลัมน์ + CHECK + สร้าง
`drawing_calibrations` และ `drawing_view_states` · การเพิ่ม `method` แยกสามจังหวะ (เพิ่มแบบว่างได้ →
backfill `typed` → ตั้ง NOT NULL) เพราะคอลัมน์ที่ห้ามว่างและไม่มี default ใส่ค่าให้แถวเดิมไม่ได้ ·
รันกับฐานแล้ว 2026-09-03 และตรวจโครงจริงด้วย `information_schema` · ย้อนกลับต้องเขียน
migration ใหม่มาถอน ไม่ใช่ `git revert`

**Testing** `quantity-provenance.test.ts` เฝ้าทะเบียน (ห้ามช่องคะแนน · ป้ายไทยล้วน ·
`requiresProposal` เฉพาะ `model`) · `takeoff-repository.integration.test.ts` insert ตรงเลี่ยง
repository แล้วพิสูจน์ว่าฐานปฏิเสธทั้งสองทิศของ CHECK · `closed-tables.test.ts` กันหลังบ้านแตะ
ตารางใหม่ทั้งสอง · กติกาข้อ 7 ต้องมีเทสต์ใน `takeoff-measurement.test.ts` ว่าแถว `typed`
ยังถูกบังคับสองมิติเหมือนเดิม ส่วนแถว `pointer`/`region_trace` รับมิติเดียว
