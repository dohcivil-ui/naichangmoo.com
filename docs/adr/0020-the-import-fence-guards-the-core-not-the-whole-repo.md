# ADR 0020: รั้ว import ล้อมชั้นคำนวณ ไม่ล้อมทั้งรีโป และรั้วต้องพิสูจน์ได้ว่ายังกัด

**Status:** Accepted — เจ้าของงานมอบให้เลือกแนวทาง 2026-08-28 ผ่านการกริลครบทุกข้อ

## Context

โค้ดในรีโปนี้ถูกเขียนโดย AI หลายเซสชันทำงานคู่ขนาน บทเรียนที่จ่ายจริงมาแล้วหลายรอบคือ
กฎที่เป็นแค่ข้อความในเอกสารจะถูกเผลอละเมิด ส่วนกฎที่เป็นกลไก (hook กันกรอกรหัสผ่าน,
scanner ของ IP-091, เทสต์ G1–G16 ของ ADR 0019) อยู่รอด คำถามของฉบับนี้คือ กติกา
"ชั้นคำนวณห้ามรู้จักโลกภายนอก" ควรเป็นกลไกด้วยหรือไม่ และเข้มแค่ไหน

ของจริงก่อนฉบับนี้: `src/lib` เกือบบริสุทธิ์อยู่แล้ว (ไม่มี next/react เลย เทสต์ 671 ตัวจบใน
ไม่กี่วินาทีเพราะไม่ต้องต่อฐานข้อมูล) AI SDK ถูก import ที่เดียวคือ `src/server/ai/provider.ts`
ตามรอยต่อของ IP-131 ผู้ละเมิดมีไฟล์เดียวคือ `src/lib/auth.ts` ที่ลาก `@/db` เข้า lib
และไม่มีเครื่องมือใดห้ามคนต่อไปทำแบบเดียวกัน

## Decision

1. **strict เฉพาะไข่แดง ไม่ strict ทั้งรีโป** — รั้วล้อมสามโซน:
   - `src/lib` ห้าม import ฐานข้อมูล, `src/server` (ตอนรัน), หน้าจอ, เฟรมเวิร์ก และ SDK ภายนอก
   - AI SDK (`openai`, `@anthropic-ai/sdk`) เข้าได้ประตูเดียวคือ `src/server/ai/provider.ts`
   - `src/app` กับ `src/components` แตะฐานข้อมูลตรงไม่ได้ ต้องผ่าน `src/server`
   หน้าเว็บฝั่ง Next.js ที่เหลือปล่อยตามธรรมชาติของเฟรมเวิร์ก ไม่บังคับ ports & adapters เต็มรูป
2. **ใช้กฎ `@typescript-eslint/no-restricted-imports` ที่ติดตั้งอยู่แล้ว** ไม่เพิ่ม dependency
   และอนุญาต `import type` ข้ามรั้วในโซนที่ระบุ เพราะ type หายไปตอน compile ไม่ใช่การพึ่งพาจริง
3. **ย้าย `auth.ts` กับ `auth-session.ts` ไป `src/server`** แทนการเจาะรูยกเว้นให้รั้ว —
   รั้วที่มีรูตั้งแต่วันแรกคือรั้วที่สอนทุกคนว่ารูเจาะได้
4. **รั้วต้องพิสูจน์ได้ว่ายังกัด** — `src/architecture-fence.test.ts` ยิงโค้ดละเมิดใส่ ESLint
   ตัวจริงทุกครั้งที่รันเทสต์ ถอดโซนออกจาก config เมื่อไหร่เทสต์แดงทันที (พิสูจน์แล้ว:
   ถอดรั้วออก เทสต์ล้ม 4 ตัว) pre-commit ที่รัน lint + test อยู่แล้วจึงบังคับรั้วโดยอัตโนมัติ
5. **ห้ามผู้เขียนโค้ด — คนหรือ AI — แก้โซนรั้วหรือเทสต์เฝ้ารั้วเพื่อให้งานของตัวเองผ่าน**
   การย้ายเส้นรั้วโดยชอบคือแก้ ADR ฉบับนี้ก่อน แล้วแก้ config กับเทสต์พร้อมกันในรุ่นเดียว

## Alternatives considered

| Alternative | Why not selected |
|---|---|
| hexagonal architecture แบบ strict ทั้งรีโป | server component ของ Next.js ถูกออกแบบให้หน้าหยิบข้อมูลเองตรงๆ การบังคับ interface + DI ทุกหน้าเพิ่มไฟล์หลายเท่าโดยหน้า landing/market ไม่ได้อะไรคืน และการรื้อใหญ่ชนกับเซสชันคู่ขนาน |
| ติดตั้ง eslint-plugin-boundaries หรือ dependency-cruiser | ทรงพลังกว่า แต่เพิ่มของใหม่ที่ต้องเรียนรู้และดูแล ในเมื่อ `no-restricted-imports` ที่มีอยู่ครอบสามโซนนี้ได้ครบ |
| จดข้อยกเว้นให้ `auth.ts` อยู่ `src/lib` ต่อ | รูถาวรในรั้ววันแรกทำให้ข้อยกเว้นถัดไปของ่ายขึ้นทุกครั้ง คน import มีสองสามจุด ย้ายถูกกว่าเฝ้า |
| เขียนกฎห้ามไว้ในเอกสารอย่างเดียว | คือสภาพเดิมที่พาให้ `auth.ts` หลุดเข้า lib ตั้งแต่แรก กฎที่ไม่มีเครื่องบังคับคือกฎที่พังเงียบ |
| เทสต์เฝ้ารั้วแบบอ่านข้อความใน config | ข้อความอยู่ครบแต่รั้วตายเป็นไปได้ (เช่น สะกดชื่อ rule ผิด) การยิงโค้ดละเมิดจริงพิสูจน์พฤติกรรม ไม่ใช่ตัวอักษร |

## Consequences

- `src/lib/auth.ts` → `src/server/auth.ts` และ `src/lib/auth-session.ts` → `src/server/auth-session.ts`
  จุด import ทั้ง 13 จุดชี้ตามไปแล้ว `auth-availability` กับ `auth-client` ยังอยู่ `src/lib`
  เพราะตัวแรกอ่านแค่ env ตัวหลังเป็นตัวช่วยฝั่ง client ที่ไม่แตะโครงสร้างพื้นฐานฝั่ง server
- เทสต์เฝ้ารั้วเพิ่มเวลารันชุดเทสต์ราวสองวินาที แลกกับการที่รั้วถูกพิสูจน์ทุกครั้งที่ commit
- แอปใหม่ทุกแอปได้กติกานี้ฟรีตั้งแต่ไฟล์แรก: สูตรคำนวณอยู่ `src/lib` แล้วจะถูกบังคับให้บริสุทธิ์เอง
- โซนของรั้วไม่ครอบ `src/data`, `scripts/`, และไฟล์ config — เข้มขึ้นภายหลังได้โดยแก้ฉบับนี้
