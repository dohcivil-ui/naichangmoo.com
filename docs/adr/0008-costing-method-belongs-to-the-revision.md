# ADR 0008: วิธีคิดราคาเป็นของ revision ไม่ใช่ของโครงการ

**Status:** Accepted — แทนที่ ADR 0007

## Context

ADR 0007 ตัดสินว่าโครงการหนึ่งเลือกสายคิดราคาได้สายเดียว เก็บที่ `projects.project_path`
และห้ามเปลี่ยนเมื่อมี revision ที่คำนวณแล้ว ข้อสรุปนั้นเข้า v0.17.0 ไปแล้วพร้อม migration `0002`
จึงต้องมี ADR ฉบับใหม่มาแทน ไม่ใช่แก้ฉบับเดิมทับ เพราะโค้ดและ migration ที่มีอยู่ถูกสร้างขึ้นตามมัน
และคนที่มาอ่าน `0002` ในอนาคตต้องหาคำอธิบายเจอว่าทำไม `project_path` เคยมีอยู่

การทบทวนก่อนเริ่มชั้นราคาพบสามเรื่องที่ ADR 0007 ตอบไม่ได้

**หนึ่ง — สายเดียวต่อโครงการตอบเคสที่พบบ่อยที่สุดไม่ได้** ผู้รับเหมาเอกชนที่ประมูลงานราชการต้องรู้
สองเลขบนปริมาณชุดเดียวกัน คือราคากลางที่เป็นเพดานและเป็นจุดอ้างอิงว่าคู่แข่งจะลงมาแค่ไหน
กับต้นทุนและกำไรของตัวเองว่าถ้าเสนอที่ 95% ของราคากลางแล้วเหลืออะไร ADR 0007 บังคับให้เลือกหนึ่ง
ซึ่งแปลว่าต้องสร้างสองโครงการแล้วถอดปริมาณสองรอบ — ขัดกับเหตุผลข้อเดียวกับที่ 0007 ใช้ตีตก
ทางเลือก "แยกเป็นสอง app" และขัดกับที่ 0007 เขียนเองว่าผู้รับเหมาเอกชนคือกลุ่มที่จ่ายเงิน

ที่สำคัญกว่านั้น ADR 0007 ข้อ 6 ระบุเองว่า `estimate_revisions` เก็บชื่อสายที่ใช้ไว้แล้ว และ
`DATA_MODEL.md` วาง `government_form_projections` ผูกกับ revision ไม่ใช่ project สายคิดราคา
จึงอยู่ที่ revision อยู่แล้วโดยพฤตินัย `projects.project_path` เป็นข้อมูลซ้ำที่รอวันขัดกันเอง

**สอง — ชื่อ `private | government` อธิบายว่าใครเป็นเจ้าของงาน ไม่ใช่ว่าคำนวณด้วยวิธีไหน**
ซึ่งเป็นคนละเรื่องกัน บริษัทเอกชนทำงานราชการเป็นเรื่องปกติ และ `organization_kind` ก็มีค่า
`government` อยู่แล้วโดยมีความหมายคนละอย่าง สองคอลัมน์นี้ไม่ correlate กันเลยแต่ชื่อชวนให้คิดว่า correlate

**สาม — ชั้นถอดปริมาณเป็นกลางเรื่องเงินได้ แต่ไม่เป็นกลางเรื่องฟอร์ม** ตรวจ
`km/ตย ปร1-6 ราชมงคล..xlsx` แล้วพบว่าแบบฟอร์มราชการบังคับโครงสร้างที่ ADR 0007 ไม่ได้พูดถึงเลย

```
ปร.5(ก) สรุปค่าก่อสร้าง        ค่างานต้นทุน | Factor F | ค่าก่อสร้าง
ปร.5(ข) สรุปค่าครุภัณฑ์จัดซื้อ   ค่างาน       | ภาษี     | ค่าก่อสร้าง    <- ไม่มี Factor F
ปร.4(พ) ค่าใช้จ่ายพิเศษ         จำนวน | หน่วย | ค่าใช้จ่ายรวม           <- ไม่มีทั้งคู่
```

สูตร `ราคากลาง = ค่างานต้นทุน × Factor F` ที่ ADR 0007 เขียนเป็นก้อนเดียวจึงใช้กับทุกรายการไม่ได้
ถ้าคูณทั้งหมด ยอดจะเกินจริงทันทีที่โครงการมีครุภัณฑ์ และเกินแบบเงียบเพราะทุกเลข "ถูก" ตามสูตรที่เขียนไว้
นอกจากนี้ ปร.1–ปร.3 ไม่ใช่เอกสารราคาแต่เป็นแบบฟอร์มถอดแบบสำรวจ และ ปร.2 แยกคอลัมน์เหล็กเสริม
ตามขนาดเส้น ซึ่งปัจจุบันข้อมูลนั้นอยู่ในข้อความอิสระของ `takeoff_items.description` ทั้งหมด

## Decision

**ปริมาณชุดเดียว รองรับหลายวิธีคิดราคาพร้อมกัน โดยวิธีคิดเป็นของ revision**

1. **Costing Method อยู่ที่ `estimate_revisions`** ค่าเป็น `factor_f | contractor_cost`
   โครงการเดียวมี revision ทั้งสองแบบบนปริมาณชุดเดียวกันได้ และเพราะ revision เป็นขอบเขตที่แช่แข็งแล้ว
   จึงไม่มีคำว่า "เปลี่ยนวิธีกลางคัน" ให้ต้องออกกฎห้าม อยากได้อีกวิธีก็ออก revision ใหม่

2. **ชื่อบอกวิธีคำนวณ ไม่บอกเจ้าของงาน** ไม่ใช้คำว่า `private`/`government` ที่ชนกับ
   `organization_kind` และไม่ใช้ `cost_plus` ซึ่งเป็นชื่อประเภทสัญญาจ้างที่มีความหมายตายตัวอยู่แล้ว

3. **ลบ `projects.project_path` และ enum `project_path`** ด้วย migration ใหม่
   ถ้าต้องการถามผู้ใช้ตั้งแต่เปิดโครงการเพื่อประโยชน์ด้าน UX ให้เก็บเป็น preference นอกตาราง `projects`
   ไม่ใช่คอลัมน์ที่ logic ใดอ่านได้

4. **เลขลำดับ revision นับแยกตามวิธีคิด** unique เป็น `(project_id, costing_method, revision_number)`
   เพราะเลข revision ไปโผล่บนเอกสารที่ยื่นจริงและถูกอ้างในหนังสือโต้ตอบ เลขที่กระโดดหาย
   โดยอธิบายไม่ได้เป็นปัญหาตอนถูกตรวจ ผลคือโครงการไม่มี "ฉบับปัจจุบัน" เดี่ยว ๆ
   หน้าจอต้องแสดงฉบับล่าสุดของทั้งสองวิธีคู่กันเสมอ

5. **`price_sets` บันทึกทั้งที่มาและปลายทาง** เพิ่มแหล่งอำนาจ (ทางการ / ขององค์กร) ซึ่งเป็น
   ข้อเท็จจริงว่าตัวเลขมาจากไหน และวิธีคิดที่ชุดนั้นทำไว้ใช้ revision แบบ `factor_f` ต้องใช้ชุดที่มาจาก
   แหล่งทางการเท่านั้น การเอาราคาทางการไปใช้ฝั่งผู้รับเหมาไม่ได้ถูกห้าม แต่ต้องคัดลอกเป็นชุดใหม่
   ที่บันทึกต้นทางไว้ เพื่อไม่ให้ตัวเลขของบริษัทถูกอ้างว่าเป็นราคาทางการ

6. **Cost Item Treatment เป็น enum สามค่าที่ติดมากับรายการใน cost catalogue**
   งานก่อสร้าง / ครุภัณฑ์จัดซื้อ / ค่าใช้จ่ายพิเศษตามข้อกำหนด ไม่ใช่ค่าที่ตั้งใหม่รายโครงการ
   ค่าใช้จ่ายพิเศษซึ่งเป็นของเฉพาะโครงการอยู่ใน catalogue scope ระดับองค์กรที่เพิ่มเองได้
   ต่างจาก scope กลางที่ล็อก

7. **แต่ละ Treatment มีตัวคูณของตัวเองที่ระดับแผ่น ปร.5 ไม่ใช่ภาษีรายบรรทัด**
   ตรวจกับชุด สตง. ภูมิภาคที่ 12 แล้ว ปร.5(ข) มีคอลัมน์หัวว่า "ภาษีมูลค่าเพิ่ม 7%" แต่สิ่งที่พิมพ์
   ในช่องนั้นคือ **1.07 ซึ่งเป็นตัวคูณ ไม่ใช่จำนวนเงินภาษี** ใบนั้นจึงมีรูปเดียวกับ ปร.5(ก) ทุกประการ

   ```
   ปร.5(ก) งานก่อสร้าง     ค่างานต้นทุน x Factor F 1.2957
   ปร.5(ข) ครุภัณฑ์จัดซื้อ    ค่างานต้นทุน x 1.07
   ปร.4(พ) ค่าใช้จ่ายพิเศษ   ไม่มี ปร.5 และไม่มีตัวคูณ ยกยอดรวมเข้า ปร.6 ตรง ๆ
   ```

   โมเดลที่ถูกจึงเป็น **หนึ่งกลไก ไม่ใช่สอง** คือ `ค่างานต้นทุนรวมของหมวด x ตัวคูณของหมวดนั้น`
   โดยที่มาของตัวคูณต่างกัน — Factor F มาจากตารางที่รัฐประกาศและรวมภาษีไว้แล้ว ส่วน 1.07 คือ
   อัตราภาษีมูลค่าเพิ่มล้วน ๆ และค่าใช้จ่ายพิเศษมีตัวคูณเท่ากับหนึ่ง

   สิ่งที่ผมเคยเขียนไว้ว่าเป็น "ภาษีต่อบรรทัด" ผิด ใบจริงคิดที่ระดับหมวด ไม่ใช่ระดับรายการ
   ข้อความในแบบฟอร์มเปล่าที่ว่า "รายการใดต้องชำระภาษีมูลค่าเพิ่ม ให้รวมค่าภาษีมูลค่าเพิ่มด้วย"
   ใช้กับการตั้งยอดใน ปร.4(พ) ไม่ใช่การเพิ่มคอลัมน์ภาษีรายบรรทัด

8. **ปร.4 และ ปร.5 แยกตาม Cost Item Treatment แต่ ปร.6 มีใบเดียวที่รวมทุกหมวด**
   ตรวจกับชุดจริงของโครงการ สตง. ภูมิภาคที่ 12 (เพชรบุรี) แล้ว ปร.6 เขียนหัวว่า `แผ่นที่ 1/1`
   และมีสามแถวคือ หมวด 1 หมวดงานอาคาร, หมวด 2 หมวดงานครุภัณฑ์จัดซื้อหรือสั่งทำ และ
   หมวด 3 ค่าใช้จ่ายพิเศษ แล้วรวมเป็นราคากลางเดียว

   ดังนั้นความสัมพันธ์คือ **หลาย ปร.4/ปร.5 ไหลเข้า ปร.6 ใบเดียว** ไม่ใช่ชุดเอกสารที่ขนานกัน

   ```
   ปร.4 (ก1..กN)  ──►  ปร.5(ก)  ──┐
   ปร.4 (ข)       ──►  ปร.5(ข)  ──┼──►  ปร.6 แผ่นที่ 1/1  ──►  คิดเป็น
   ปร.4 (พ)       ─────────────────┘
   ```

   ปร.4 ของงานก่อสร้างแยกใบตามกลุ่มงานแล้วใส่เลขกำกับ ก1, ก2, … และแบ่งหน้าภายในกลุ่มงานนั้นเอง
   ส่วน ปร.4(พ) ไม่มี ปร.5 รองรับเลย สิ่งที่โมเดลต้องตอบได้คือแต่ละหมวดใน ปร.6 มาจากใบไหน
   และใบนั้นมาจาก ปร.4 ใบไหน โดยยอมรับว่าหนึ่งในสามเส้นทางข้ามชั้น ปร.5 ไป

   หัวใบ ปร.4 ยังมีช่อง **แบบเลขที่/แผ่นที่** ที่อ้างช่วงแผ่นแบบของกลุ่มงานนั้น (ใบจริงเขียน `P16 - P37`)
   ซึ่ง schema ปัจจุบันยังไม่มีที่เก็บ ทั้งที่เป็นร่องรอยที่เชื่อมปริมาณกลับไปหาแบบโดยตรง

9. **Factor F เป็นชุดข้อมูลที่มีรุ่นของตัวเอง และ `document_baseline_versions` อ้างถึงรุ่นที่ใช้คู่กัน
   พร้อมตรึงค่าที่คาดหวังไว้ใน fixture ของตัวเอง** ADR 0007 สร้าง registry ของ Factor F ขึ้นมา
   โดยไม่อ้างถึง baseline registry ที่ `estimeter-operating-policy.md` วางไว้แล้ว ซึ่งเป็นสองที่ปกครอง
   ของชิ้นเดียวกัน สองอย่างนี้เปลี่ยนคนละจังหวะ — ตาราง Factor F เปลี่ยนเมื่อรัฐประกาศอัตราดอกเบี้ยใหม่
   ส่วนแบบฟอร์มเปลี่ยนเมื่อออกหลักเกณฑ์ฉบับใหม่ การอ้างถึงกันแทนการยุบรวมจึงทำให้ต่างฝ่าย
   เปลี่ยนได้ตามจังหวะตัวเอง และ fixture ที่ตรึงค่าไว้ทำให้การแก้ dataset ข้างใต้พังเสียงดัง
   แทนที่จะออกตัวเลขใหม่เงียบ ๆ

   **ชุดข้อมูลมี work type เป็นกุญแจด้วย ไม่ใช่มีแต่งานอาคาร** ชุดที่ลงไว้แล้วใน
   `src/data/factor-f/cgd-w481-be2569.json` มี 48 ตาราง คือ 4 ประเภทงาน (อาคาร, ทาง,
   สะพานและท่อเหลี่ยม, ชลประทาน) คูณกับ 12 ชุดตามเงินล่วงหน้าจ่ายและเงินประกันผลงานหัก
   แต่ละตารางมี 24 ช่วงค่างานต้นทุน และคอลัมน์ที่รวมภาษีเท่ากับคอลัมน์ Factor คูณ 1.07
   ซึ่งเป็นกลไก VAT ตัวแรกในข้อ 7 ในรูปธรรม

   ชุดนั้นบันทึก issuer, เลขหนังสือ, วันที่, sha256 ของไฟล์ต้นทาง, อัตราดอกเบี้ยที่อ้าง
   และ `reviewedBy` ที่ยังว่างพร้อมข้อความห้ามใช้คำนวณจนกว่าจะมีผู้มีคุณวุฒิตรวจ —
   ตรงกับที่ ADR ฉบับนี้และ 0007 กำหนดไว้ทั้งสองฉบับ

10. **การปัดเศษเป็นนโยบายของ baseline version ไม่ใช่ค่าคงที่ในโค้ด และมีมากกว่าหนึ่งจุด**
    ตรวจกับชุดจริงของโครงการ สตง. ภูมิภาคที่ 12 (เพชรบุรี) แล้วได้ภาพนี้

    ```
    ทุกบรรทัดใน ปร.5(ก)   ค่างานต้นทุน x Factor F ปัดสองตำแหน่ง
    รวมใน ปร.5(ก)         7,358,914.87 x 1.2957 = 9,534,945.997059 -> 9,534,946.00
    ปร.6 บรรทัด "คิดเป็น"  15,213,876.48 -> 15,213,000.00        <- ตัดลงหลักพัน
    ```

    **แต่ละแผ่นตัดเศษคนละหน่วย และนั่นไม่ใช่ความขัดแย้ง** ปร.6 ตัดลงหลักพันที่บรรทัด "คิดเป็น"
    ตามชุดนี้ ส่วน ปร.5 ตัดลงหลักร้อยที่บรรทัดยอดสุทธิ ตามชุด อาคารฟอกไต ปุญโญภาส
    (3,296,598.64 → 3,296,500.00) สองกฎอยู่คนละแผ่นจึงอยู่ด้วยกันได้ ใบ สตง. ไม่ได้ตัดที่ ปร.5(ก)
    เพราะแผ่นนั้นไม่ได้พิมพ์บรรทัดยอดสุทธิ ไม่ใช่เพราะกฎต่างกัน

    ทั้งสองเป็น **กฎการแสดงผล ไม่ใช่การคำนวณ** ยอดที่คำนวณได้ยังอยู่บนแผ่นเหนือบรรทัดที่ตัด
    เพื่อให้ผู้อ่านเห็นว่ายอมทิ้งไปเท่าไร ใบ สตง. ทิ้ง 876.48 บาทระหว่าง "รวม" กับ "คิดเป็น"
    ถ้าเอาค่าที่ตัดแล้วไปแทนที่ค่าที่คำนวณได้ จะเป็นการซ่อนสิ่งที่แบบฟอร์มออกแบบมาให้เห็น

    `src/lib/thai-baht.ts` มี `floorToHundredBaht` และ `floorToThousandBaht` แยกกันตามนี้
    พร้อม test ที่ยันกับตัวเลขบนใบจริงทั้งสองชุด และ `document_baseline_versions` ยังมีสิทธิ์
    กำหนดทับได้ถ้าหลักเกณฑ์ฉบับใหม่เปลี่ยนหน่วย

11. **Factor F เลือกครั้งเดียวจากค่างานต้นทุนรวมของหมวด แล้วใช้ค่าเดียวกันทุกบรรทัด**
    ใบจริงใช้ 1.2957 เท่ากันทั้ง 21 บรรทัด ทั้งที่ค่างานต่อบรรทัดต่างกันตั้งแต่ 25,885 ถึง 1,532,372
    การเปิดตาราง Factor F ตามค่างานของแต่ละบรรทัดจะให้ราคากลางผิดทั้งใบ และผิดแบบที่ยอดรวม
    ยังดูสมเหตุสมผล จึงเป็นกฎที่ต้องเขียนเป็น test ไม่ใช่ comment

    ใบนี้ยังใช้ **ดอกเบี้ยเงินกู้ 5%** ซึ่งไม่ใช่ทั้ง 7% ของ ว499 และ 6% ของ ว481 เป็นหลักฐาน
    เพิ่มว่าอัตราดอกเบี้ยเปลี่ยนหลายรอบ และ revision ต้องอ่านย้อนได้ว่าใช้ตารางรุ่นไหน

12. **ปร.1–ปร.3 เลื่อน ไม่ตัด** ทั้งสามเป็นแบบฟอร์มถอดแบบสำรวจ และ ปร.2 ต้องการปริมาณเหล็กเสริม
    แยกตามขนาดเส้น ซึ่งทำไม่ได้ตราบใดที่สเปกวัสดุยังอยู่ในข้อความอิสระ **ต้องเติมสเปกวัสดุ
    แบบมีโครงสร้างก่อนเปิดให้ผู้ใช้จริงกรอกปริมาณ** ไม่ใช่ก่อนจบ release ใด release หนึ่ง
    เพราะเส้นตายที่แท้จริงคือจุดที่ข้อมูลของคนอื่นเริ่มเข้าระบบ และเงื่อนไขนี้ต้องอยู่ในที่ที่บล็อกได้จริง
    ไม่ใช่ในหัวข้ออนาคตของ roadmap

13. **คำถามว่าจะคิดราคาแบบไหนย้ายไปอยู่ก่อนขั้นตั้งราคา** `getWorkflowBlocker` เลิกกั้นขั้นที่หนึ่ง
    ด้วยสายงาน เพราะขั้นที่หนึ่งยังไม่มี revision ให้เลือกวิธี การเลือกจริงเกิดตอนสร้าง revision
    ส่วนตัวกั้นที่ขั้นตั้งราคามีไว้บอกผู้ใช้ล่วงหน้าว่ากำลังจะต้องตอบอะไร

## Alternatives considered

| Alternative | Why not selected |
|---|---|
| คงตาม ADR 0007 คือสายอยู่ที่โครงการ เปลี่ยนไม่ได้ | บังคับให้ผู้รับเหมาที่ประมูลงานราชการสร้างสองโครงการและถอดปริมาณสองรอบ ซึ่งเป็นเหตุผลเดียวกับที่ 0007 ใช้ตีตกทางเลือกแยกสอง app |
| โครงการมีสายหลักหนึ่งสาย แล้วเปิดมุมมองเทียบอีกสายแบบอ่านอย่างเดียว | มุมมองที่คำนวณแล้วแต่ไม่มี revision รองรับ คือตัวเลขที่ไม่มีใครรับผิดชอบและอ้างอิงย้อนไม่ได้ |
| เก็บ `projects.project_path` ไว้เป็นค่าตั้งต้นของ revision ใหม่ | ฝากความหวังไว้กับวินัยว่าจะไม่มีใครเอาไปใช้เป็น gate ซึ่งเป็นสิ่งที่จะมีคนเผลอทำ และเป็นความซ้ำแบบเดียวกับที่ ADR นี้ตั้งใจกำจัด |
| ให้ `costing_method` ผูกกับ `price_sets` แบบข้ามไม่ได้เลย | ปิดเคสที่ถูกต้อง คือผู้รับเหมาใช้ราคาทางการเป็นตัวตั้งต้นก่อนหาราคาจริง สิ่งที่ต้องกันมีทิศทางเดียวคือสายราชการเผลอใช้ราคาที่ไม่เป็นทางการ |
| ให้ Cost Item Treatment เป็น boolean ว่าคูณ Factor F หรือไม่ | แบบฟอร์มจริงมีสามการปฏิบัติ ไม่ใช่สอง boolean จะบีบสามให้เหลือสองแล้วต้องแตกใหม่ทันทีที่เจอครุภัณฑ์ |
| ให้ Cost Item Treatment แก้ได้รายโครงการ | เปิดช่องให้ยอดเปลี่ยนโดยไม่มีใครเห็น การปฏิบัติต่อรายการเป็นเรื่องที่หลักเกณฑ์กำหนด ไม่ใช่เรื่องที่แต่ละโครงการเลือก |
| ยุบ Factor F เข้าไปใน `document_baseline_versions` | อัตราดอกเบี้ยประกาศใหม่ทีหนึ่งต้องออก baseline version ใหม่ของฟอร์มทั้งชุด แล้วรัน fixture ของฟอร์มใหม่หมดทั้งที่ฟอร์มไม่ได้เปลี่ยนสักช่อง |
| เก็บกฎปัดเศษไว้ในโค้ดตามที่ implement อยู่แล้ว | หลักเกณฑ์ฉบับใหม่เปลี่ยนกฎได้ และ baseline registry มีช่อง rounding policy รออยู่แล้ว การทิ้งไว้ในโค้ดแปลว่าการเปลี่ยนหลักเกณฑ์กลายเป็นการแก้โปรแกรม |
| เขียนทับ ADR 0007 ในเลขเดิม | 0007 ปล่อยไปแล้วใน v0.17.0 และ migration `0002` ถูกสร้างตามมัน การเขียนทับจะลบร่องรอยว่าทำไม `project_path` เคยมีอยู่ |

## Consequences

- **ต้องมี migration ใหม่ที่ลบ `projects.project_path` และ enum ของมัน** และเพิ่ม
  `costing_method` เข้า `estimate_revisions` พร้อมเปลี่ยน unique index เป็นสามคอลัมน์
  ฐานข้อมูลยังเป็น dev ล้วน จึงยังไม่ต้องมี approval record ตาม AGENTS.md
- **`getWorkflowBlocker` และ test ของมันต้องแก้พร้อมกัน** เพราะ test ปัจจุบันยืนยันพฤติกรรม
  การกั้นขั้นที่หนึ่งด้วยสายงานไว้ตรง ๆ
- **`DATA_MODEL.md` มีชื่อฟอร์มที่ไม่มีอยู่จริง** บรรทัด `government_form_projections` เขียนว่า
  ผลิต ปร.4(ก) ซึ่งไม่มี ของจริงคือ ปร.4 กับ ปร.4(พ) ต้องแก้พร้อมกับเพิ่มแนวคิดชุดเอกสาร
- **โค้ดชั้นราคาจะมีหลายทางเดินตลอดไป** ทั้งตามวิธีคิดและตาม Cost Item Treatment
  ซึ่งยาวกว่าทางเดียวที่ตั้งค่าได้ แต่เป็นความยาวที่สะท้อนความจริงของโดเมน
- **หน้าจอรายการโครงการต้องแสดงสองยอด** เพราะคำถามว่าโครงการนี้ล่าสุดเท่าไรมีสองคำตอบจริง ๆ
  การบีบให้เหลือหนึ่งคือการซ่อนความจริงจากผู้ใช้
- **ถ้าจะเปลี่ยนกลับ** ต้องเขียน ADR ใหม่ และต้องตอบให้ได้ว่าจะทำอย่างไรกับ revision
  ที่คำนวณด้วยวิธีที่กำลังจะถูกยกเลิก
