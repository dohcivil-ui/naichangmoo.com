# ADR 0012: สิทธิ์ผู้ดูแลแพลตฟอร์มเป็นแถวที่ถูกมอบให้ ไม่ใช่ธงบนบัญชี

**Status:** Accepted

## Context

โปรเจกต์มี `member_role` (`owner`, `admin`, `member`, `viewer`) อยู่แล้ว แต่มันผูกกับ `organization_members` คือเป็น admin ของ *องค์กรหนึ่ง* ไม่ใช่ของแพลตฟอร์ม ปัจจุบันจึงไม่มีใครที่ระบบจะตรวจสิทธิ์ด้วยได้เลยเมื่อมีคนขอแก้ราคาหรือตั้งโปรโมชัน

งานที่รออยู่คือ back-office ที่เขียนเนื้อหาที่ลูกค้าเห็น — ราคา ช่วงลดราคา ข้อความระดับสิทธิ์ AGENTS.md กำหนดว่า "Do not make a customer-visible or irreversible change without an explicit user authorization recorded in an approval/audit record" และ "Prefer server-side authorization checks over hiding UI controls" ทั้งสองข้อบังคับว่าต้องรู้ให้ได้ว่า *ใคร* ได้รับอนุญาต และรู้จากฝั่งเซิร์ฟเวอร์

คำถามที่ต้องตอบคือสิทธิ์นี้เก็บเป็นอะไร และครอบคลุมแค่ไหน

## Decision

**สิทธิ์ผู้ดูแลแพลตฟอร์มเก็บเป็นแถวในตาราง `platform_administrators`** ไม่ใช่คอลัมน์บน `users` และไม่ใช่รายชื่ออีเมลใน environment variable

แต่ละแถวบันทึก ผู้ได้รับสิทธิ์ ผู้มอบสิทธิ์ เวลาที่มอบ และเวลาที่ถอน แถวที่ถูกถอนไม่ถูกลบ เพราะคำถามที่การตรวจสอบจะถามคือ "วันที่ 15 มีนาคม ใครแก้ราคาได้บ้าง" ซึ่งตอบไม่ได้ถ้าเก็บแค่สถานะปัจจุบัน

**การมอบและการถอนสิทธิ์เขียน `audit_events` เสมอ** ด้วย `actorId` ของผู้มอบ ไม่ใช่ผู้รับ

**ขอบเขตของสิทธิ์นี้จำกัดไว้ที่เนื้อหาของแพลตฟอร์ม** — ราคา ช่วงลดราคา ข้อความระดับสิทธิ์ ทะเบียนแอป และตัวเลขสรุปเชิงรวม

**สิทธิ์นี้ไม่ให้สิทธิ์อ่านข้อมูลงานขององค์กรใด** ผู้ดูแลแพลตฟอร์มเปิดโครงการ แบบก่อสร้าง บรรทัดวัด หรือชุดราคาของลูกค้าไม่ได้ การอ่านข้อมูลเหล่านั้นยังถูกจำกัดด้วย `projects.organization_id` เหมือนเดิม คนที่ดูแลข้อความบนหน้าเว็บไม่มีเหตุผลใดต้องเห็นตัวเลขในโครงการของลูกค้า และการรวมสองอย่างนี้เข้าด้วยกันจะทำให้บัญชีเดียวที่ถูกยึดกลายเป็นการรั่วของข้อมูลทั้งแพลตฟอร์ม

**ผู้ดูแลคนแรกมาจากสคริปต์ break-glass** `scripts/grant-platform-admin.mjs` รับอีเมลอย่างชัดแจ้ง เขียนทั้งแถวและ audit event และ **ปฏิเสธถ้ามีผู้ดูแลที่ยังไม่ถูกถอนอยู่แล้วแม้แต่คนเดียว** มันจึงเป็นทางเริ่มต้น ไม่ใช่ประตูหลังที่ใช้ได้ตลอดเวลา หลังจากนั้นการมอบสิทธิ์ทำโดยผู้ดูแลที่มีอยู่เท่านั้น

**การตรวจสิทธิ์อยู่ฝั่งเซิร์ฟเวอร์และ fail closed** `requirePlatformAdmin()` เป็นทางเดียวที่พื้นผิวผู้ดูแลใช้ตรวจ ถ้าอ่าน session ไม่ได้ อ่านฐานข้อมูลไม่ได้ หรือไม่พบแถวที่ยังไม่ถูกถอน ผลลัพธ์คือปฏิเสธ ไม่ใช่อนุญาต การซ่อนปุ่มบน UI ไม่นับเป็นการตรวจสิทธิ์

## Alternatives considered

| Alternative | Why not selected now |
|---|---|
| คอลัมน์ `users.platform_role` | บันทึกสถานะได้ แต่ไม่บันทึกว่าใครมอบและเมื่อไร การถอนสิทธิ์จะลบประวัติทิ้ง ทำให้ตอบไม่ได้ว่าย้อนหลังใครมีสิทธิ์อยู่บ้าง |
| รายชื่ออีเมลใน environment variable | ง่ายที่สุดและไม่ต้อง migration แต่สิทธิ์กลายเป็น config ที่ไม่มีร่องรอยในฐานข้อมูล ตรวจสอบย้อนหลังไม่ได้ ต้อง deploy ใหม่ทุกครั้งที่เปลี่ยนคน และผูกตัวตนกับอีเมลซึ่งเปลี่ยนมือได้ |
| ใช้ `member_role = "admin"` ขององค์กรที่กำหนดให้เป็นองค์กรแพลตฟอร์ม | ไม่ต้องสร้างอะไรใหม่ แต่รวมสองความหมายเข้าด้วยกัน วันที่มีคนเพิ่มสมาชิกเข้าองค์กรนั้นโดยไม่รู้ความหมายพิเศษ คือวันที่มอบสิทธิ์ทั้งแพลตฟอร์มโดยไม่ตั้งใจ |
| ให้ผู้ดูแลแพลตฟอร์มอ่านข้อมูลทุกองค์กรได้ด้วย | สะดวกเวลาต้องช่วยลูกค้าแก้ปัญหา แต่ทำให้บัญชีเดียวที่ถูกยึดเปิดข้อมูลทั้งระบบ ถ้าวันหน้าต้องการสิทธิ์สนับสนุนลูกค้าจริง ต้องเป็นสิทธิ์คนละตัวที่มีการยินยอมของเจ้าของข้อมูลและมีอายุจำกัด ไม่ใช่ผลพลอยได้ของสิทธิ์แก้ข้อความ |
| ให้ใครก็ตามที่เป็น `owner` ขององค์กรใดก็ได้ เข้าหลังบ้าน | ทุกคนที่สมัครใช้งานได้เป็น owner ขององค์กรตัวเองโดยอัตโนมัติ เท่ากับไม่มีการจำกัดสิทธิ์เลย |

## Consequences

**Migration** เพิ่มตาราง `platform_administrators` หนึ่งตาราง ไม่แก้ตารางเดิม ไม่มีข้อมูลที่ต้องย้าย

**Bootstrap** ระบบที่ยังไม่มีผู้ดูแลจะเข้าหลังบ้านไม่ได้เลยจนกว่าจะรันสคริปต์ ซึ่งเป็นพฤติกรรมที่ต้องการ ระบบที่เปิดหลังบ้านให้ก่อนแล้วค่อยหาว่าใครควรเข้าได้ คือระบบที่เปิดหลังบ้านให้ทุกคนช่วงหนึ่ง

**การถอนสิทธิ์ตัวเองได้ และการถอนคนสุดท้ายได้** ถ้าถอนผู้ดูแลคนสุดท้ายออก ระบบจะกลับไปสู่สภาพที่ต้องใช้สคริปต์ break-glass ซึ่งยอมรับได้ เพราะสคริปต์นั้นต้องเข้าถึงฐานข้อมูลโดยตรงอยู่แล้ว การเขียนกฎห้ามถอนคนสุดท้ายจะสร้างบัญชีที่ถอนไม่ได้ ซึ่งแย่กว่า

**Testing** ต้องมีเทสต์ที่ยืนยันว่าไม่มี session แล้วปฏิเสธ, มี session แต่ไม่มีแถวแล้วปฏิเสธ, มีแถวที่ถูกถอนแล้วปฏิเสธ และอ่านฐานข้อมูลไม่ได้แล้วปฏิเสธ — สามข้อหลังคือจุดที่ระบบส่วนใหญ่พลาดโดยการ fail open

**Security** ขอบเขตที่จำกัดไว้เป็นสิ่งที่ต้องรักษา ทุกครั้งที่มีใครอยากให้หน้าหลังบ้านแสดงข้อมูลของลูกค้ารายหนึ่ง คำถามที่ต้องถามคือสิทธิ์นั้นควรเป็นสิทธิ์คนละตัวหรือไม่ ไม่ใช่ขยายสิทธิ์นี้ให้กว้างขึ้นทีละนิด
