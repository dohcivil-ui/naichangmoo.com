## รูปแบบไฟล์และโฟลเดอร์

- ชั้นแกนธุรกิจอยู่ `src/lib/` เป็นตรรกะล้วน · ฝั่งเซิร์ฟเวอร์อยู่ `src/server/` · หน้าจออยู่ `src/components/`
  แยกตามโซน (`platform` `landing` `admin` `estimeter` `pricing` `prototype` `icons` `ui`)
- **วางไฟล์ทดสอบไว้ข้างไฟล์จริงคู่กันเสมอ** — `factor-f.ts` คู่กับ `factor-f.test.ts` ในโฟลเดอร์เดียวกัน
  ไม่มีโฟลเดอร์ `__tests__` แยก
- ด่านตรวจระดับทั้งระบบวางไว้ที่ราก `src/` ชื่อลงท้าย `-fence.test.ts`
- ชื่อไฟล์ใช้ kebab-case ทั้งหมด (`app-registry-form.tsx` ไม่ใช่ `AppRegistryForm.tsx`)

## Component

- เขียนเป็น function component ของ React 19 · ชื่อ component เป็น PascalCase แต่ชื่อไฟล์เป็น kebab-case
- ระบบหน้าตาเป็น **CSS class ใน `globals.css` บวก component ที่เขียนเอง** ไม่มี UI library ภายนอก
  และแทบไม่ได้ใช้ utility class ของ Tailwind — เขียนคลาสเองอย่าง `.button--primary` `.gl-*` `.work-plan__*`
- ปุ่มใช้ระบบคลาสเดิม `.button` คู่กับ `.button--primary` `.button--orange` `.button--ghost`

## Shared Component — ใช้ของเดิมก่อนเสมอ

**ห้ามสร้าง Component Library ล่วงหน้าเพียงเพราะยังไม่มี** สร้าง Shared Component (ของกลาง)
เมื่อพบรูปแบบที่ซ้ำจริงและพฤติกรรมเหมือนกันจริงเท่านั้น

- มีของกลางอยู่แล้วให้ใช้ของเดิม — App Shell, Assistant Dock, `ThaiDateField`, ไอคอนใน `components/icons/`
- ตารางตอนนี้มี 4 ระบบแยกกัน (`takeoff` `admin` `work-plan` `gl-*`) **ก่อนรวมต้องสำรวจก่อนว่ารวมได้แค่ไหน**
  ไม่ใช่รวมทันทีเพราะเห็นว่าซ้ำ
- Modal, Toast, Empty State, Badge ยังไม่มีของกลาง ให้สร้างเมื่อมีการใช้ซ้ำจริง ไม่ใช่สร้างเผื่อ
- **ห้ามสร้าง pattern ใหม่เองถ้าของเดิมใช้ได้** และห้ามทำข้อยกเว้นเฉพาะหน้าถ้ายังแก้ที่ของกลางได้

## Design Token — ห้าม Hardcode เมื่อมีค่ากลาง

- **สีมาจาก `src/app/globals.css` บล็อก `:root` ที่เดียว** ห้ามเขียนค่าสีดิบในคอมโพเนนต์ (บังคับด้วยรั้วสี)
  ต้องใช้ค่าเดียวกันในโค้ด TypeScript ให้อ่านผ่าน `src/lib/kitchen-colours.ts` ไม่ใช่พิมพ์เลขซ้ำ
- **สีที่ใช้ซ้ำหรือมีความหมายเชิงสถานะ** (error, success, muted) ให้ยกขึ้นเป็น token ใน `:root`
  ส่วนสีที่ใช้ครั้งเดียวไม่ต้องบังคับเป็น token — เป้าหมายคือแก้ที่เดียวแล้วทุกที่ที่มีความหมายเดียวกันเปลี่ยนตาม
- spacing, radius, shadow และ breakpoint **จะมีชุดมาตรฐานกลาง** โดย**ไม่แปลงของเดิมทั้งระบบในคราวเดียว**
  ประกาศ token ใหม่ก่อน แล้วค่อยเปลี่ยนเมื่อไปแตะส่วนนั้นอยู่แล้วหรือมีเหตุผลชัดเจน
- เพิ่ม token ใหม่ต้องเสนอเหตุผลและรอเจ้าของงานอนุมัติก่อน แล้วจึงเพิ่มเข้าแหล่งค่ากลาง

## ไอคอนและสัญลักษณ์

- **ห้าม Emoji** ทั้งใน UI, commit message, เอกสาร และข้อความที่ตอบเจ้าของงาน
- อักขระอย่าง `✓` `○` `→` ที่ทำหน้าที่เป็นไอคอนหรือปุ่ม ให้เปลี่ยนเป็น SVG ตามระบบไอคอน
  แต่ถ้าเป็นเครื่องหมายวรรคตอนหรือข้อความธรรมดา ไม่ห้าม — **ห้ามทำด่านที่แบนอักขระเหล่านี้แบบเหมารวม**
- ไอคอนใหม่ให้ตรวจของเดิมใน `components/icons/` ก่อน ถ้าไม่มีต้องถามเจ้าของงานว่าจะเอา SVG ที่เขียนเอง
  หรือภาพที่เขาไปสร้างจากเครื่องมือภายนอก **AI เลือกแทนเองไม่ได้**
- จุดไข่ปลาในข้อความสถานะใช้ `…` ตัวเดียว ไม่ใช่จุดสามตัว

## Error handling และสถานะระดับหน้า

- ตรวจสิทธิ์ด้วยนโยบายฝั่งเซิร์ฟเวอร์ทุก action ที่ต้องป้องกัน **ห้ามอาศัยการซ่อนปุ่มบนหน้าจอ**
- Loading, Error และ Not Found ให้ทำเป็นรูปแบบกลางสำหรับ route ที่ใช้งานจริงและจำเป็น
  **ไม่บังคับสร้างไฟล์ครบทุก route เพียงเพื่อให้ครบกฎ**
- ค่าที่ไม่มีที่มาครบห้ามเข้าการคำนวณ ชุดข้อมูลที่ยังไม่มีผู้มีคุณวุฒิรับรองต้องประกาศสถานะนั้นออกมา
  ให้ผู้เรียกปฏิเสธได้ (ดู `docs/rules/engineering.md`)

## Testing และการตรวจงาน

- Quality gate ก่อน commit — `pnpm typecheck` แล้ว `pnpm lint` แล้ว `pnpm test`
  แล้ว `node scripts/check-roadmap.mjs`
- **เทสต์ผ่านไม่ใช่หลักฐานว่าใช้ได้จริง** งานที่มีหน้าจอต้องเปิดดูของจริงผ่าน `chrome-devtools` MCP
  (ซึ่งบนเครื่องนี้รัน Microsoft Edge) งานฝั่งเซิร์ฟเวอร์ที่ไม่มีอะไรเรนเดอร์ก็ต้องยิงจริงหนึ่งครั้ง
  ผ่านทางเดียวกับที่แอปจะใช้ ตัวอย่างวิธีทำอยู่ที่ `scripts/smoke-assistant.ts`
- **ห้ามเขียนสคริปต์ Puppeteer หรือ Playwright เอง** เพื่อคุมเบราว์เซอร์
- schema เปลี่ยนต้องมาพร้อม migration ของ Drizzle ที่ผ่านการทบทวน ผลกระทบด้านสิทธิ์ แผนย้อนกลับ และเทสต์
  **ห้ามใช้ `db push` แทนกระบวนการ migration จริง**
